# Systems Mastery 2.1 — Compilation, Linking, and Object Files

> Source code becomes a runnable program through multiple transformations and contracts. Compilation translates code, linking connects compiled components, and loading prepares an executable for execution. Success at one stage does not guarantee success at the next.

---
# Objective

Phase 1 established how the CPU executes ISA-defined instructions and why compiler optimizations can produce unexpected machine-code sequences. In Module 1.5, GCC replaced source-level arithmetic with `LEA` instructions; inspecting the generated code was essential to understanding what actually ran.

Module 2.1 asks a preceding question:

> How does readable C source become machine code that can be linked, loaded, and executed?

The goal is to explain this transformation, diagnose failures at its boundaries, and inspect the artifacts rather than treating `gcc` as a black box. C is used here as an instrument for investigating systems, not as a separate language course.

---
# Core Pipeline

```text
C source + headers
        ↓ preprocessing
translation unit
        ↓ compilation
assembly representation
        ↓ assembly
relocatable object file
        ↓ linking with other objects/libraries
executable (possibly with shared-library dependencies)
        ↓ OS loading and, when needed, dynamic loading
runtime startup → main() → program execution
```

This is a conceptual pipeline: compilers may integrate stages internally rather than launching separate programs for every step.

Each boundary answers a different question:

| Stage | Responsibility | Example failure |
|---|---|---|
| Preprocessing | Expand includes and macros | Missing header |
| Compilation | Analyze C and generate lower-level code | Invalid syntax or incompatible types |
| Assembly | Encode instructions and record references | Invalid assembler instruction |
| Linking | Combine compiled components and resolve references | Undefined or duplicate symbols |
| Loading | Map and prepare an executable and its dynamic dependencies | Missing or incompatible shared library |
| Execution | Run instructions according to the target ISA | Runtime fault or incorrect behavior |

A program may pass the compiler yet fail at linking; it may link correctly yet fail when loaded on another machine.

# Preprocessing Produces a Translation Unit

Consider the program investigated during the module:

```c
#include <stdio.h>

int main(void)
{
    printf("Hello, Systems Mastery!\n");
    return 0;
}
```

The command:

```bash
gcc -E hello.c -o hello.i
```

stops after preprocessing. The `#include` directive is replaced with header contents, including transitively included declarations and types. The resulting `.i` file is still C source, not executable machine code.

**Observed experiment:**

```text
$ wc -l hello.c hello.i
    7 hello.c
  733 hello.i
  740 total
```

The expanded source contained a declaration equivalent to:

```c
extern int printf(const char *__restrict __format, ...);
```

**Observation:** preprocessing expanded seven source lines into 733 lines and made a declaration for `printf` available.

**Interpretation:** a header provides information needed to compile calls, not necessarily the implementation of the called function. The extra lines need not all originate directly in `stdio.h`.

A **translation unit** is the source resulting from preprocessing a source file. Each translation unit can be compiled separately.

---
# Declarations, Definitions, and Separate Compilation

A declaration tells the compiler that a function exists and describes its interface:

```c
int sum(int a, int b);
```

A definition supplies the implementation:

```c
int sum(int a, int b)
{
    return a + b;
}
```

A simple modular arrangement is:

```c
/* math.h */
int sum(int a, int b);
```

```c
/* math.c */
#include "math.h"
int sum(int a, int b) { return a + b; }
```

```c
/* main.c */
#include "math.h"
int main(void) { return sum(3, 5); }
```

Compile independently and link together:

```bash
gcc -c main.c -o main.o
gcc -c math.c -o math.o
gcc main.o math.o -o app
```

The `-c` option produces an object file without linking. `main.o` can contain a call to `sum` without containing its implementation: the missing destination is represented as a symbol reference for later resolution.

The exercises established two contrasting failure modes:

```bash
gcc main.o -o app     # omitted math.o: undefined reference to sum
```

If a non-`static` function body is instead defined in a header included in multiple `.c` files, each object may define the same external symbol, resulting in a **multiple definition** link error. Headers commonly provide declarations, while one source file provides the external definition. Exceptions exist, such as intentionally `static inline` functions, but were not required in this module.

**Build implication:** changing only the implementation in `math.c` normally requires recompiling that translation unit and relinking. Changing a shared header may require recompiling all translation units that depend on it, directly or indirectly—not necessarily every file in the project.

---
# Assembly Is Not Yet an Object File

GCC can expose distinct stages:

```bash
gcc -E hello.c -o hello.i    # preprocessed C
gcc -S -O0 hello.c -o hello.s  # assembly text
gcc -c hello.s -o hello.o     # machine code in an object file
```

Assembly is a human-readable representation of instructions and directives. The assembler encodes instructions into bytes appropriate for the target ISA and produces an object containing sections, symbols, and possibly relocation records.

An object file can contain valid CPU instructions without being independently launchable as a Linux program.

---
# ELF Object Files and Symbols

The learner inspected the object file using `file` and `nm`:

```text
$ file hello.o
hello.o: ELF 64-bit LSB relocatable, x86-64, version 1 (SYSV), not stripped

$ nm hello.o
                 U _GLOBAL_OFFSET_TABLE_
0000000000000000 T main
                 U puts
```

**Observed:** the artifact was an **ELF relocatable** file for x86-64. `main` was defined in `.text` (`T`); `puts` was undefined in this object (`U`). `_GLOBAL_OFFSET_TABLE_` was also referenced.

GCC had emitted a reference to `puts` for this simple formatted print. This shows why generated output must be inspected rather than inferred solely from source text.

An ELF file is a container format, not a synonym for an executable. Linux uses ELF for relocatable objects, executables, and shared objects. The number shown for `main` in this object is a section-relative value, **not** evidence that the program will execute at absolute address zero.

Conceptually, relevant object-file information includes:

```text
.text       machine instructions
.rodata     read-only constants, including string literals
symbols     known definitions and unresolved names
relocations places and rules for adjusting references
```

---
# Relocations: Identifying What Must Be Patched

The learner ran:

```bash
readelf -r hello.o
```

The observed output included:

```text
Relocation section '.rela.text' contains 2 entries:
Offset          Type              Symbol + Addend
00000000000b    R_X86_64_PC32     .rodata - 4
000000000010    R_X86_64_PLT32    puts - 4

Relocation section '.rela.eh_frame' contains 1 entry:
000000000020    R_X86_64_PC32     .text + 0
```

The `.rela.text` records identify where address-dependent operands need adjustment, which symbol or section they refer to, and which relocation calculation to use. One reference addresses the string in `.rodata`; another addresses the function call involving `puts`.

On x86-64, relative addressing often expresses a target as a displacement from the next instruction. A relocation enables the appropriate displacement to be computed once layout or linkage is known.

The `.eh_frame` relocation supports unwind-related metadata and was not explored further.

**Important boundary:** a relocation record does not itself supply the final runtime address of a dynamically linked function. Static linkers and runtime dynamic linkers may participate in different parts of resolving an executable's references.

---
# Linking Combines Contracts, Not Merely Byte Sequences

The linker combines relevant sections and reconciles symbol definitions with references. It may adjust encoded displacements and generate metadata for dynamic dependencies.

```text
main.o: call to sum (undefined symbol)
math.o: definition of sum
            ↓
         linker
            ↓
app: usable reference to sum
```

The distinction matters in debugging:

- `undefined reference` means the linker cannot find a required definition among the provided inputs and allowed libraries.
- `multiple definition` means incompatible duplicate external definitions were supplied.
- Neither is corrected merely by adding an `#include` that contains only a declaration.

The module's separate-compilation and linker-error scenarios were discussed and diagnosed interactively. Complete terminal logs for those particular builds were not provided; their outcomes are illustrated here as expected behavior, not as measured experimental output.

---
# Static and Dynamic Linking

**Static linking** incorporates selected compiled library code into the linked artifact. It can simplify deployment of those dependencies but may increase output size and requires rebuilding/relinking to pick up embedded library updates.

**Dynamic linking** records dependencies on shared libraries. Compatible shared code can be reused across executables, but deployment now depends on finding a suitable library and resolving its required symbols and versions.

These choices are not determined by whether a library is part of the operating system or privately developed. They depend on how the program is built and linked.

A typical production failure discussed during assessment was:

```text
./app: /lib/x86_64-linux-gnu/libc.so.6:
version `GLIBC_2.38' not found
```

This does **not** mean compilation or build-time linking necessarily failed. The executable may have linked successfully on its build machine, while the target machine's dynamic loader cannot satisfy its required glibc symbol versions. Building against an older, supported glibc baseline can improve compatibility with target environments, subject to other platform and dependency constraints.

Useful diagnostics include `ldd --version`, `ldd ./app` and suitable ELF inspection tools. `ldd` should not be used indiscriminately on untrusted executables.

---
# Linking Is Not Loading

The operating system prepares the executable's process image and transfers control to its designated entry point, with the dynamic loader involved when required. The C runtime startup path eventually invokes `main`.

```text
ELF executable
     ↓
OS loader / dynamic loader as applicable
     ↓
ELF entry point (typically _start)
     ↓
C runtime startup
     ↓
main()
     ↓
termination path
```

The learner inspected a Linux executable named `hello`:

```text
$ readelf -h hello | grep Entry
  Entry point address:               0x1060

$ nm hello | grep -E '(_start|main)'
0000000000001060 T _start
0000000000001149 T main
                 U __libc_start_main@GLIBC_2.34
```

The full `nm` output also included symbols for BSS/data boundaries. The decisive observation is **entry point `0x1060` = `_start`**, not `main` at `0x1149`.

`__libc_start_main` indicates glibc participation in the startup path. This experiment establishes the entry point and symbols in the file; it does not trace every instruction executed by the runtime loader.

---
# ISA and Executable-Format Compatibility

An ELF file for x86-64 and an ELF file for ARM64 share a file-format family but do not contain interchangeable machine instructions. Copying an x86-64 executable to an ARM64 Linux machine does not make it native ARM64 code.

The assessment used an illustrative `Exec format error` scenario to reinforce the Phase 1 distinction:

```text
ELF: packaging and load metadata
ISA: instruction encodings and architectural semantics
ABI: conventions and binary compatibility contracts
```

A target-specific build, cross-compilation, or appropriate emulation is needed. The compatible ISA alone is not sufficient to guarantee every runtime dependency and ABI requirement is satisfied.

# Compiler Optimization Changes the Generated Program

The final hands-on experiment compared assembly for:

```c
int square(int x)
{
    return x * x;
}
```

Commands:

```bash
gcc -S -O0 square.c -o square_O0.s
gcc -S -O2 square.c -o square_O2.s
```

The learner provided the generated assembly. Relevant instructions were:

**`-O0`:**

```asm
endbr64
pushq %rbp
movq  %rsp, %rbp
movl  %edi, -4(%rbp)
movl  -4(%rbp), %eax
imull %eax, %eax
popq  %rbp
ret
```

**`-O2`:**

```asm
endbr64
imull %edi, %edi
movl  %edi, %eax
ret
```

**Observation:** `-O2` removed the stack-frame setup and teardown and the stack store/load. It used the 32-bit register `%edi` directly for the multiplication and copied the result into `%eax`, the conventional integer return register on this target ABI.

**Explanation:** optimization can remove unnecessary intermediate memory traffic while preserving the function's required behavior. `%edi` and `%eax` are the 32-bit portions of x86-64 registers; `endbr64` is associated with control-flow security mechanisms rather than the arithmetic itself.

**Not established:** no runtime timing benchmark was performed for this `square` comparison. Fewer instructions in a disassembly do not independently prove a quantified speedup; this connects directly to Module 1.5's discussion of latency, throughput and microarchitecture.

# Practical Debugging Perspective

A build/deployment investigation should begin by identifying the boundary at which evidence indicates failure:

| Symptom | First thing to inspect |
|---|---|
| Header not found | Preprocessor include paths |
| Invalid C expression | Compiler diagnostic and translation unit |
| Undefined symbol | Link inputs, declarations, definitions, `nm` |
| Duplicate external definition | Header implementation placement and object symbols |
| Wrong binary architecture | `file`, ELF machine type, target ISA |
| Shared library or symbol version unavailable | Runtime environment and dynamic dependencies |
| Unexpected generated code | Optimization flags and assembly/disassembly |

Tools used during the module included `gcc`, `file`, `nm` and `readelf`. The objective is not to memorize their flags but to ask a specific question about an artifact and choose evidence that can answer it.

---
# Core Mental Model

```text
Source expresses intent.
Declarations make interfaces visible within a translation unit.
Compilation produces machine-code artifacts.
Symbols identify definitions and unresolved references.
Relocations describe address-dependent adjustments.
Linking combines artifacts and establishes references.
ELF metadata describes the resulting binary.
Loading prepares it for execution.
Runtime startup precedes main().
The CPU executes instructions defined by the target ISA.
```

The engineering discipline is to keep **source, object, executable, load environment and running process** conceptually distinct.

# Final Takeaway

A successful compilation does not guarantee a successful link; a successful link does not guarantee a successful load; a successful load does not guarantee correct execution.

> Inspect the artifact at the failing boundary, determine which contract it must satisfy, and verify that contract with evidence rather than guessing from the source code.
