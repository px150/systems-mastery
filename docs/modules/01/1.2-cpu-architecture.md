# Systems Mastery 1.2 — CPU Architecture

> CPU architecture defines the programmer-visible machine model through which instructions transform architectural state.

---

# Objective

The previous module established that computers represent information through finite patterns of bits.

Those patterns do not contain their own meaning.

Meaning comes from the contract used to interpret them.

A pattern may represent:

```text
an integer

a character

a memory address

a flag field

part of a machine instruction
```

Machine instructions therefore require an interpretation contract just as data does.

But representation alone does not explain execution.

A processor must maintain the current state of a running computation, determine which instruction comes next, perform operations on values, access memory and alter control flow.

This module asks the next systems question:

> What architectural state does a CPU expose, and how do machine instructions transform that state during program execution?

The purpose is not to learn assembly programming or the internal implementation of a particular processor.

The purpose is to construct a machine-level mental model involving:

```text
registers
+
Program Counter
+
flags
+
instructions
+
ALU
+
Control Unit
+
Instruction Set Architecture
```

and to understand execution as a sequence of state transformations.

---

# The Need for Processor State

Consider a simple computation:

```text
5 + 3
```

The processor needs somewhere to hold the values currently participating in the computation.

Conceptually:

```text
R0 = 5
R1 = 3
```

After addition:

```text
R2 = 8
```

The original values do not necessarily disappear:

```text
R0 = 5
R1 = 3
R2 = 8
```

The operation modifies only the state specified by the instruction.

This leads to an important principle:

> Executing an instruction changes some parts of machine state while leaving others unchanged.

---

# Registers

Registers are small storage locations directly exposed by the processor architecture.

Conceptually:

```text
R0 = 0000 0101
R1 = 0000 0011
R2 = 0000 0000
```

An operation such as:

```text
R2 ← R0 + R1
```

produces:

```text
R0 = 0000 0101
R1 = 0000 0011
R2 = 0000 1000
```

Registers contain bit patterns.

Just as in binary representation, the bits themselves do not determine their meaning.

For example:

```text
1111 1111
```

inside a register could participate in an operation as:

```text
an unsigned value

a signed value

an address

a bit field

part of some other representation
```

The interpretation depends on the instruction and the architectural contract.

---

# General-Purpose and Special-Purpose Registers

Not every register has the same architectural role.

Some registers are primarily used to hold ordinary operands and intermediate values.

These are commonly described as:

```text
general-purpose registers
```

Other registers have specific architectural roles.

Examples include:

```text
Program Counter

Stack Pointer

status or condition state
```

The exact set of registers and their rules depend on the Instruction Set Architecture.

---

# Register Width

Registers have finite width.

A conceptual 8-bit register can contain:

```text
2⁸ = 256
```

different patterns.

A 32-bit register can contain:

```text
2³²
```

patterns.

A 64-bit register can contain:

```text
2⁶⁴
```

patterns.

The width determines how much state can be represented in that register, but it does not by itself determine what the bits mean.

A processor described as:

```text
64-bit
```

should not be interpreted as:

> Every register and every operation in the processor is necessarily 64 bits wide.

Real architectures can expose registers and operations of several widths.

Instead, the term indicates important architectural widths associated with that ISA, commonly including general-purpose operations and address representation.

---

# The Arithmetic Logic Unit

Values stored in registers must be transformed.

The component responsible for many fundamental arithmetic and logical operations is the:

```text
Arithmetic Logic Unit
```

or:

```text
ALU
```

Typical ALU operations include:

```text
addition
subtraction
AND
OR
XOR
shifts
comparisons
```

Conceptually:

```text
R0 = 5
R1 = 3

        ↓

       ALU
      ADD

        ↓

R2 = 8
```

The ALU should not be confused with the CPU as a whole.

It does not independently decide which instruction should execute next.

It performs particular transformations as part of the processor's execution machinery.

---

# Instructions

A processor operates according to machine instructions.

A conceptual instruction might be written:

```text
ADD R2, R0, R1
```

This expresses:

```text
R2 ← R0 + R1
```

The instruction contains an operation:

```text
ADD
```

and operands:

```text
R2
R0
R1
```

Conceptually:

```text
ADD        → opcode / operation

R2         → destination

R0, R1     → sources
```

The exact syntax is not important.

At the machine level, the instruction itself is represented by bits.

---

# Instructions Are Bit Patterns

The processor does not receive textual instructions such as:

```text
ADD R2, R0, R1
```

It receives machine-code bit patterns.

Conceptually:

```text
instruction bits
      ↓
architectural interpretation
      ↓
operation + operands
```

A particular bit pattern does not intrinsically mean:

```text
ADD
```

The meaning exists because an architecture defines that interpretation.

This extends the central principle from binary representation:

> Bits acquire meaning through a contract.

For machine instructions, that contract is provided by the Instruction Set Architecture.

---

# The Program Counter

A processor must also know which instruction belongs to the current point in execution.

This information is represented by a special architectural register commonly called the:

```text
Program Counter
```

or:

```text
PC
```

On some architectures it has another name.

For example, x86-64 uses:

```text
RIP
```

Conceptually:

```text
PC = 100
```

means that execution is currently associated with the instruction at the location identified by `100`.

If instructions execute sequentially:

```text
100 → instruction A
101 → instruction B
102 → instruction C
103 → instruction D
```

the Program Counter progresses through the instruction stream:

```text
100
 ↓
101
 ↓
102
 ↓
103
 ↓
104
```

The Program Counter is therefore part of the state required to describe where execution currently is.

---

# Sequential Execution

Consider:

```text
100: instruction A
101: instruction B
102: instruction C
```

If:

```text
PC = 100
```

the first instruction executes.

The architectural state then changes so that execution continues with:

```text
PC = 101
```

After the next instruction:

```text
PC = 102
```

This creates the familiar appearance of instructions executing one after another.

But sequential execution is not the only possibility.

---

# Control Flow Is State Change

Suppose execution reaches:

```text
102: JUMP 500
```

The processor does not physically move instructions around.

Instead, the instruction changes the Program Counter:

```text
PC = 500
```

Execution therefore continues from another location.

This provides a machine-level model of control flow:

> A jump changes the architectural state that determines which instruction executes next.

High-level constructs such as:

```text
if

while

for

function calls
```

ultimately depend on mechanisms that alter control flow.

---

# Condition Flags

Programs frequently need control flow to depend on the result of a computation.

For example:

```c
if (a == b) {
    ...
}
```

A processor may expose condition or status flags representing properties of previous operations.

Common examples include concepts such as:

```text
Zero

Negative

Carry

Overflow
```

The exact flags and their semantics depend on the ISA.

Conceptually:

```text
CMP R0, R1
```

may compare two values and update a Zero flag.

If:

```text
R0 = 5
R1 = 5
```

then:

```text
Zero flag = 1
```

A later conditional jump might inspect that state:

```text
JZ 200
```

If the relevant condition is true:

```text
PC = 200
```

Otherwise execution continues sequentially.

---

# Comparison and Conditional Branching

Consider:

```text
100: CMP R0, R1
101: JZ  200
102: ADD R2, R0, R1
```

with:

```text
R0 = 5
R1 = 5
Zero flag = 0
PC = 100
```

After comparison:

```text
R0 = 5
R1 = 5
Zero flag = 1
PC = 101
```

The comparison did not need to modify either operand.

It changed condition state.

The next instruction observes that state:

```text
JZ 200
```

and changes:

```text
PC = 200
```

The instruction at:

```text
102
```

is therefore not executed.

Conditional control flow can thus be understood as interaction between:

```text
operation result
+
condition state
+
Program Counter
```

---

# Memory Addresses

Registers can also contain bit patterns interpreted as memory addresses.

Suppose:

```text
R0 = 1000
```

The value:

```text
1000
```

may be interpreted as the address of a memory location.

Conceptually:

```text
memory[1000] = 5
```

An instruction can then transfer data between memory and registers.

For example:

```text
LOAD R1, [R0]
```

means conceptually:

```text
R1 ← memory[R0]
```

If:

```text
R0 = 1000
memory[1000] = 5
```

then afterward:

```text
R0 = 1000
R1 = 5
```

The address remains in `R0`.

The value found at that address is copied into `R1`.

---

# Loading and Storing

Data movement can be modeled with two conceptual operations:

```text
LOAD
STORE
```

For example:

```text
LOAD R2, [R0]
```

means:

```text
R2 ← memory[R0]
```

while:

```text
STORE [R0], R2
```

means:

```text
memory[R0] ← R2
```

The distinction is important:

```text
R0
```

refers to the value stored in the register itself.

While:

```text
[R0]
```

conceptually refers to the memory location whose address is stored in `R0`.

The notation is useful for reasoning about architecture, but learning assembly syntax is not an objective of this module.

---

# A Complete State Transformation

Consider:

```text
R0 = 1000
R1 = 5
R2 = 0

memory[1000] = 3
```

and:

```text
LOAD  R2, [R0]
ADD   R2, R2, R1
STORE [R0], R2
```

After the load:

```text
R0 = 1000
R1 = 5
R2 = 3
```

After the addition:

```text
R0 = 1000
R1 = 5
R2 = 8
```

After the store:

```text
memory[1000] = 8
```

while:

```text
R0 = 1000
R1 = 5
R2 = 8
```

The sequence can therefore be viewed as a succession of state transformations.

---

# Architectural State

The processor exposes a collection of information describing the current execution state.

This is its:

```text
architectural state
```

Conceptually, this includes:

```text
general-purpose registers

Program Counter

Stack Pointer

condition/status state

other ISA-visible state
```

The exact contents depend on the architecture.

The important property is that this is state visible through the architectural contract.

Execution can therefore be modeled as:

```text
S₀
 ↓
instruction
 ↓
S₁
 ↓
instruction
 ↓
S₂
 ↓
instruction
 ↓
S₃
```

or more compactly:

```text
state
→ instruction
→ new state
→ instruction
→ new state
→ ...
```

This is the central execution model of the module.

---

# Instructions as State Transformations

Consider:

```text
R0 = 5
R1 = 3
R2 = 0
PC = 100
```

and the conceptual instruction:

```text
ADD R2, R0, R1
```

Before:

```text
R0 = 5
R1 = 3
R2 = 0
PC = 100
```

After:

```text
R0 = 5
R1 = 3
R2 = 8
PC = next instruction
```

Depending on the architecture, relevant status flags may also change.

The instruction therefore does not simply "calculate 8."

It transforms architectural state according to rules defined by the architecture.

---

# The Control Unit

The processor needs hardware responsible for coordinating the actions required by instructions.

Conceptually, this role belongs to the:

```text
Control Unit
```

The Control Unit coordinates activity involving components such as:

```text
registers

ALU

instruction processing

Program Counter

memory-related operations
```

It should not be confused with the compiler.

The compiler operates before execution:

```text
source code
    ↓
compiler
    ↓
machine instructions
```

The processor then executes those already-generated instructions.

The Control Unit is part of that execution machinery.

---

# Compiler and Processor

Consider:

```c
int add(int a, int b) {
    return a + b;
}
```

The compiler translates this source-level operation into instructions appropriate for a target architecture.

Conceptually:

```text
C source
   ↓
compiler
   ↓
target ISA instructions
   ↓
machine code
   ↓
processor execution
```

Once the executable has been produced, the compiler does not need to participate every time the function executes.

The processor executes the resulting machine instructions directly.

---

# Instruction Set Architecture

The Instruction Set Architecture, or:

```text
ISA
```

defines the software-visible architectural contract of a processor family.

It includes concepts such as:

```text
available instructions

instruction semantics

architectural registers

operand forms

instruction encodings

supported architectural widths

addressing mechanisms

control-flow behavior

other architecturally visible state
```

Examples of ISAs include:

```text
x86-64

ARM64
```

The ISA determines what machine-code patterns mean to a compatible processor.

---

# ISA as a Contract

Suppose a machine-code pattern is interpreted by an x86-64 processor.

Its meaning is determined by:

```text
x86-64 ISA
```

The same bits cannot generally be assumed to represent the same instruction under:

```text
ARM64
```

This follows directly from the representation principle established in the previous module:

```text
bits
+
interpretation contract
=
meaning
```

For machine instructions:

```text
instruction bits
+
ISA
=
architectural instruction meaning
```

---

# ISA Compatibility

Consider three processors:

```text
CPU A → x86-64

CPU B → x86-64

CPU C → ARM64
```

A machine-code program compiled for x86-64 can in principle execute directly on:

```text
CPU A
CPU B
```

because both implement the same target ISA.

CPU C implements a different ISA.

The important compatibility boundary is therefore not the manufacturer or internal processor design.

It is the architectural contract expected by the machine code.

---

# ISA and Microarchitecture

Two processors can implement the same ISA while having very different internal designs.

For example:

```text
CPU A
ISA: x86-64
internal implementation: design A
```

and:

```text
CPU B
ISA: x86-64
internal implementation: design B
```

Both can implement the same architectural instruction:

```text
ADD
```

while realizing it differently internally.

One implementation might take a different number of internal stages or cycles from another.

Those implementation details belong to:

```text
microarchitecture
```

rather than to the ISA-level program model.

---

# Architecture vs Microarchitecture

The distinction can be summarized as:

```text
ISA
→ what the processor promises to software
```

while:

```text
microarchitecture
→ how a particular processor implements that promise
```

Examples of architectural concerns include:

```text
instruction semantics

architectural registers

visible flags

addressing rules

machine-code encoding
```

Examples of microarchitectural concerns include internal implementation choices such as:

```text
pipelines

execution-unit organization

internal scheduling

cache implementation
```

Detailed microarchitecture is outside the scope of this module.

---

# Same ISA, Different Implementations

Suppose two processors begin with equivalent architectural state:

```text
S₀
```

and execute the same architectural instruction.

One processor may internally realize the operation differently from the other.

What matters to software is that the architectural result obeys the ISA.

Conceptually:

```text
CPU A:

S₀
 ↓
internal implementation A
 ↓
S₁
```

and:

```text
CPU B:

S₀
 ↓
internal implementation B
 ↓
S₁
```

The internal paths may differ.

The architectural contract remains compatible.

---

# Observing the Machine Architecture

The architecture exposed by the system can be inspected directly.

On the tested Linux machine:

```bash
uname -m
```

produced:

```text
x86_64
```

The prediction before running the command was also:

```text
x86-64
```

The experiment therefore confirmed that the system exposes an x86-64 machine architecture.

This identifies an architectural target.

It does not reveal the complete internal microarchitecture of the processor.

---

# Observing Generated Instructions

A small C function provides a useful probe:

```c
int add(int a, int b)
{
    return a + b;
}
```

Compiling to assembly with optimization:

```bash
gcc -O1 -S add.c -o add.s
```

produced the relevant instructions:

```asm
leal (%rdi,%rsi), %eax
ret
```

The purpose of this experiment is not to learn x86-64 assembly syntax.

It demonstrates that a high-level operation becomes concrete target-ISA instructions.

The function conceptually performs:

```text
a + b
```

while the generated machine-level implementation uses architectural registers and instructions defined by x86-64.

---

# Register Width Probe

The C type:

```c
int
```

was inspected with:

```c
#include <stdio.h>

int main(void) {
    printf("%zu\n", sizeof(int));
    return 0;
}
```

The observed result was:

```text
4
```

Therefore, on the tested system:

```text
sizeof(int) = 4 bytes
            = 32 bits
```

The generated function returned its result through:

```text
EAX
```

which is the lower 32-bit portion of the x86-64 `RAX` register.

This demonstrates that a 64-bit architecture still supports operations on narrower values.

---

# Subregisters

x86-64 exposes different-width views of some architectural registers.

For example:

```text
RAX → 64 bits
EAX → lower 32 bits
```

Similarly:

```text
RDI → 64 bits
EDI → lower 32 bits

RSI → 64 bits
ESI → lower 32 bits
```

An operation involving a 32-bit C `int` can therefore use 32-bit architectural register views even though the machine implements a 64-bit ISA.

On x86-64, writing to a 32-bit general-purpose subregister such as:

```text
EAX
```

also clears the upper 32 bits of the corresponding 64-bit register.

That behavior is part of the architecture's semantics.

---

# Optimized and Unoptimized Code

The same C function was also compiled without optimization:

```bash
gcc -O0 -S add.c -o add.s
```

The generated code contained a longer sequence including operations such as:

```asm
pushq %rbp
movq %rsp, %rbp
movl %edi, -4(%rbp)
movl %esi, -8(%rbp)
movl -4(%rbp), %edx
movl -8(%rbp), %eax
addl %edx, %eax
popq %rbp
ret
```

The exact instruction sequence differed substantially from the optimized version.

Yet both implementations realize the same source-level function.

This demonstrates another important distinction:

> The ISA defines which operations are available and what they mean. It does not require every compiler to choose the same instruction sequence for a particular source program.

---

# Compiler Choice

A compiler targeting an ISA can often choose between several valid instruction sequences.

For example, the optimized version used:

```asm
leal (%rdi,%rsi), %eax
```

while the unoptimized version eventually used:

```asm
addl %edx, %eax
```

Both can implement the required source-level addition.

Therefore:

```text
compiler
→ chooses a valid implementation using target-ISA instructions
```

while:

```text
ISA
→ defines the available architectural operations and their meaning
```

These are different responsibilities.

---

# ISA and ABI

Another contract appears when compiled functions communicate with each other.

For example, on the tested x86-64 environment, an integer return value appears in:

```text
EAX
```

The ISA establishes that:

```text
EAX exists
```

and defines its architectural behavior.

But the rule:

```text
a function returning int places its result in EAX
```

belongs to the relevant:

```text
ABI / calling convention
```

This distinction is important.

Conceptually:

```text
ISA
→ what architectural resources and instructions exist
```

while:

```text
ABI
→ conventions allowing separately compiled code to cooperate
```

The ABI is not the central subject of this module, but recognizing the boundary prevents different system contracts from being conflated.

---

# Function Calls and Returns

Normal function calls require more than simply jumping to another instruction.

Suppose:

```text
main
 ↓
calls add
 ↓
add executes
 ↓
returns to main
```

The processor must preserve enough information to know where execution should continue after the called function finishes.

Conceptually:

```text
CALL add
```

does two important things:

```text
save return location

transfer control to add
```

A later:

```text
RET
```

retrieves the saved return location and changes the instruction pointer accordingly.

The `RET` instruction does not itself contain the return address.

It uses previously saved state.

---

# Return Address

Consider:

```text
100: CALL add
101: next instruction
```

The important return location is:

```text
101
```

not the address of `add`.

Conceptually:

```text
CALL
 ↓
save 101
 ↓
PC ← address of add
```

Later:

```text
RET
 ↓
recover 101
 ↓
PC ← 101
```

Function return is therefore another example of control flow implemented through changes to architectural state.

---

# Nested Calls and the Stack

Function calls can be nested:

```text
main
 ↓
A
 ↓
B
```

When `A` calls `B`, execution must eventually return to the appropriate point inside `A`.

When `A` later returns, execution must continue at the appropriate point inside `main`.

The return locations naturally follow:

```text
last saved
→
first restored
```

This is:

```text
LIFO
```

behavior.

A stack is therefore a natural structure for managing nested return information.

---

# Stack Pointer

The processor needs architectural state identifying the current stack position.

This role is commonly provided by the:

```text
Stack Pointer
```

On x86-64:

```text
RSP
```

is used for this purpose.

Instructions that push or remove stack data modify this state.

For example, conceptually:

```text
PUSH value
```

changes:

```text
stack memory
+
Stack Pointer
```

On x86-64, the stack conventionally grows toward lower addresses, so a push decreases `RSP` before storing the value.

The exact direction is architecture-specific.

---

# Stack-Related Assembly Observation

The unoptimized C function contained:

```asm
pushq %rbp
movq %rsp, %rbp
```

The first instruction stores the current value of `RBP` on the stack and changes stack state.

The second copies:

```text
RSP → RBP
```

It does not move the stack pointer.

After:

```asm
movq %rsp, %rbp
```

the values of `RSP` and `RBP` may identify the same address, while `RSP` itself remains unchanged by that instruction.

Again, the purpose of observing these instructions is architectural understanding rather than assembly-language mastery.

---

# Saving and Restoring Architectural State

Suppose execution of a program is interrupted and later resumed.

Saving only the Program Counter is not enough.

Consider:

```text
R0 = 5
R1 = 8
R2 = 13
PC = 500
```

If another execution context overwrites those registers, restoring only:

```text
PC = 500
```

would identify where execution should continue but would not reconstruct the data state required by that computation.

Resumption therefore requires preserving the relevant architectural state.

Conceptually:

```text
general-purpose registers

Program Counter

Stack Pointer

condition/status state

other relevant ISA-visible state
```

must be reconstructable.

---

# Architectural vs Microarchitectural State

A processor also contains internal state that software does not normally observe directly.

Examples may include information associated with:

```text
pipeline progress

internal execution machinery

implementation-specific structures
```

This is:

```text
microarchitectural state
```

It is distinct from:

```text
architectural state
```

Architectural state is the state exposed through the ISA-level machine model.

This distinction explains why execution can in principle be resumed without reconstructing the exact internal pipeline state that existed previously.

What must be preserved is the state required by the architectural contract.

---

# Fetch, Decode and Execute

At a high level, execution can be described as:

```text
fetch
 ↓
decode
 ↓
execute
```

The Program Counter identifies where the relevant instruction is located.

The processor obtains the instruction representation.

The instruction is interpreted according to the ISA.

The processor then coordinates the required operation and produces a new architectural state.

Conceptually:

```text
PC
 ↓
instruction bits
 ↓
ISA-defined meaning
 ↓
coordinated execution
 ↓
new architectural state
```

The detailed fetch-decode-execute cycle belongs to a later module.

At this stage, the important point is that instructions drive architectural state transitions.

---

# The ISA Is Not a Physical Component

It is useful to avoid saying:

```text
the ISA executes the instruction
```

or:

```text
the ISA interprets the bits
```

The ISA is not a physical processor component.

It is a specification or contract.

The processor hardware implements that contract.

Therefore:

```text
ISA
→ defines meaning
```

while:

```text
processor hardware
→ realizes that meaning
```

The distinction parallels other system contracts.

A file format specification does not physically parse a file.

A protocol specification does not physically transmit a packet.

Likewise, an ISA defines rules that processor implementations obey.

---

# Components and Contracts

The concepts introduced in this module occupy different categories.

Architectural state includes things such as:

```text
general-purpose registers

Program Counter

Stack Pointer

flags
```

Execution hardware includes components such as:

```text
ALU

Control Unit
```

The architectural contract is:

```text
ISA
```

The compiler is a software tool that targets that contract.

The microarchitecture is the internal hardware implementation used to realize it.

These concepts interact but should not be collapsed into a single layer.

---

# High-Level Control Flow

Consider:

```c
if (a == b) {
    work();
}
```

At the architectural level, this can involve:

```text
comparison
 ↓
condition state
 ↓
conditional branch
 ↓
Program Counter change
```

Similarly:

```c
while (x != 0) {
    x--;
}
```

requires execution to return to an earlier part of the instruction stream.

Conceptually:

```text
body
 ↓
condition
 ↓
branch backward
 ↓
body again
```

The loop does not require the processor to physically repeat or copy instructions.

The Program Counter is redirected.

---

# Jump vs Return

Both:

```text
JUMP
```

and:

```text
RET
```

can modify the Program Counter.

The difference is where the target comes from.

Conceptually:

```text
JUMP
→ target specified by the control-flow instruction
```

while:

```text
RET
→ target recovered from previously saved return state
```

This is why a simple jump to a function is insufficient to model a normal function call.

The system must also retain where execution should return afterward.

---

# CPU Architecture and Binary Representation

The previous module established:

```text
bits
+
interpretation
=
meaning
```

CPU architecture extends that idea.

Registers contain bit patterns.

Addresses are bit patterns.

Instructions are bit patterns.

Flags are represented by state.

The Program Counter itself contains an architectural value.

The ISA gives these representations operational meaning.

Therefore:

```text
binary representation
 ↓
architectural interpretation
 ↓
state transformation
```

connects representation directly to execution.

# The Architectural Machine Model

A useful conceptual CPU model is:

```text
                ┌────────────────────┐
                │    Control Unit    │
                └─────────┬──────────┘
                          │
          ┌───────────────┼───────────────┐
          │               │               │
          ▼               ▼               ▼
     Registers           ALU          PC / Flags
          │               │               │
          └───────────────┼───────────────┘
                          │
                          ▼
                     new state
```

This is deliberately simplified.

It is not intended to reproduce the physical layout of a modern CPU.

Its purpose is to expose the architectural relationships needed for reasoning.

---

# Execution as Repeated State Transformation

The central model can now be expressed as:

```text
architectural state S₀
        ↓
   instruction I₀
        ↓
architectural state S₁
        ↓
   instruction I₁
        ↓
architectural state S₂
        ↓
       ...
```

An instruction may modify:

```text
a register

multiple registers

flags

memory

Program Counter

Stack Pointer

other architectural state
```

while leaving other state unchanged.

Control flow itself fits the same model because changing the Program Counter is simply another architectural state transformation.

---

# Core Mental Model

When reasoning about CPU architecture, ask:

```text
What is the current architectural state?

Which register contains each relevant value?

What does the Program Counter identify?

Which instruction is being interpreted?

Which ISA defines the meaning of that instruction?

Which operands does the instruction read?

Which architectural state does it modify?

Which state remains unchanged?

Does the operation affect condition flags?

Does control flow modify the Program Counter?

Is a bit pattern being interpreted as data or as an address?

Is this behavior defined by the ISA, an ABI, the compiler, or the microarchitecture?

Am I reasoning about software-visible architecture or internal implementation?
```

The most important abstraction is:

```text
current state
+
ISA-defined instruction
=
new state
```

The compiler selects instructions compatible with the target ISA.

The ISA defines their architectural meaning.

The Control Unit coordinates their execution.

Registers hold architectural values.

The ALU performs arithmetic and logical transformations.

Flags preserve relevant condition state.

The Program Counter determines the instruction flow.

The microarchitecture determines how a particular processor internally realizes the architectural contract.

The central principle is:

> A CPU can be understood architecturally as a machine that repeatedly transforms visible state according to instructions whose meaning is defined by an ISA.

# Final Takeaway

A CPU does not directly execute C functions, loops, variables or abstract mathematical operations.

Those concepts are translated into machine instructions.

The instructions are encoded as bit patterns.

The ISA defines what those patterns mean.

The processor maintains architectural state including registers, control-flow state and status information.

Each instruction reads some of that state and produces a new state.

Therefore the essential model is:

```text
source program
      ↓
   compiler
      ↓
ISA-compatible machine instructions
      ↓
current architectural state
      +
instruction
      ↓
processor execution
      ↓
new architectural state
      ↓
next instruction
      ↓
...
```

At the architectural level:

> Program execution is a sequence of ISA-defined transformations of machine state.
