# Systems Mastery 1.5 — Performance Fundamentals

> Performance is the rate at which useful work completes, constrained by dependencies, data availability, control flow, available parallelism and implementation mechanisms.

---
# Objective

Instruction Execution established that a running program performs ISA-defined architectural state transformations. It also established that fetch–decode–execute is a conceptual description, not a guarantee that modern processors finish one instruction before beginning another.

Performance Fundamentals asks the next question:

> If two programs produce the correct result, why can they require different amounts of time?

The central transition is from thinking about *which operations are required* to thinking about *how quickly useful work can progress*.

```text
same architectural result
≠
same execution time

same instruction count
≠
same execution time
```

The goal is not to memorize CPU specifications. It is to learn how to formulate, test and explain performance hypotheses.

---
# Performance Requires an Observable Quantity

Calling one program “faster” requires specifying what is being compared.

For a simple benchmark, the observable quantity may be **elapsed time**: the wall-clock interval between beginning and ending the measured work.

```text
same intended work
+
less elapsed time
=
better observed completion time
```

Elapsed time can include scheduling delays and other system activity. **CPU time** instead measures time during which a process or its threads actually consume CPU execution time; it is not interchangeable with elapsed time, particularly with parallel execution.

A timing measurement tells us **what happened**, not necessarily **why** it happened.

---
# Instruction Count Does Not Determine Execution Time

Consider two sequences containing four additions:

```text
A — dependent
R1 = R0 + 1
R2 = R1 + 1
R3 = R2 + 1
R4 = R3 + 1
```

```text
B — independent
R1 = A + 1
R2 = B + 1
R3 = C + 1
R4 = D + 1
```

Both contain four additions. Assume their initial operands are already available in registers.

In A, every operation must wait for the previous result. In B, there is no such dependency between the additions.

```text
A: R0 → R1 → R2 → R3 → R4

B: A → R1
   B → R2
   C → R3
   D → R4
```

The second sequence offers more opportunity for overlapping work. Whether that opportunity can be exploited depends on the processor’s microarchitecture.

---
# Latency and Throughput

**Latency** is how long an operation takes to produce a result needed by a dependent operation.

**Throughput** is how much work can complete per unit time.

These quantities are related but not identical.

Suppose one addition has a latency of three cycles, but the processor can begin one new *independent* addition each cycle.

```text
           cycle
           1  2  3  4  5  6
ADD 1      X  X  X
ADD 2         X  X  X
ADD 3            X  X  X
ADD 4               X  X  X
```

The four independent additions can finish after six cycles. Four strictly dependent additions would require twelve cycles in the corresponding idealized model.

Increasing each addition’s latency to five cycles need not reduce the **steady-state** throughput of one addition per cycle, provided the implementation can maintain enough overlapping operations.

```text
latency
→ time until one result is ready

throughput
→ rate of completed work
```

High throughput does not imply low latency.

---
# Clock Cycles and Frequency

A clock cycle is a useful timing reference for synchronous processor mechanisms.

```text
frequency = cycles per second
```

At a constant frequency, an execution requiring fewer cycles finishes sooner. But a higher frequency does not guarantee fewer cycles.

In a conceptual comparison:

| | CPU A | CPU B |
|---|---:|---:|
| Frequency | 4 GHz | 3 GHz |
| Cycles required | 2 billion | 1.5 billion |
| Execution time | 0.5 s | 0.5 s |

Both complete the work in the same time.

The number of cycles can depend on instruction dependencies, memory behavior, control flow, execution resources and microarchitecture.

Real processors can also vary their operating frequencies; the table assumes constant frequencies for the calculation.

---
# Instruction Dependencies

A **true data dependency** exists when an operation requires a value produced by an earlier operation.

```text
R1 = R0 + 1
R2 = R1 + 1
R3 = R2 + 1
```

The next operation cannot use a result that does not yet exist.

Dependencies constrain available overlap, even on sophisticated processors.

Independent operations give the CPU more scheduling freedom. They do not guarantee simultaneous execution: hardware resources and other constraints can still limit progress.

---
# Instruction-Level Parallelism

**Instruction-level parallelism (ILP)** describes opportunities to make progress on multiple independent instructions over overlapping intervals.

```text
independent instructions
↓
more scheduling freedom
↓
possible overlap
↓
greater throughput
```

ILP is a property of the available work and its dependencies. The degree to which ILP is exploited depends on the implementation.

The learner predicted that four independent arithmetic chains could outperform one long dependency chain even when both perform the same number of updates. This hypothesis was later tested experimentally.

---
# Pipelines

A pipeline allows different operations to occupy different processing stages during overlapping time intervals.

Consider a **conceptual** five-stage pipeline, with one cycle per stage:

```text
           cycle
           1  2  3  4  5  6  7  8
ADD 1      1  2  3  4  5
ADD 2         1  2  3  4  5
ADD 3            1  2  3  4  5
ADD 4               1  2  3  4  5
```

Without overlap, four operations of five cycles each would take twenty cycles. In this idealized pipeline, the four operations complete in eight cycles.

Pipelining improves potential **throughput**, not necessarily the latency of an individual operation. Real processors do not universally implement this five-stage structure.

---
# Pipeline Stalls

A **stall** occurs when some work cannot advance normally because a required condition or resource is unavailable.

Potential causes include:

```text
unavailable dependency result
memory data not ready
unresolved control flow
busy execution resources
```

A stall need not stop every part of a modern processor. Independent operations may continue while another dependency chain is blocked.

---
# Memory Latency Propagates Through Dependencies

Consider:

```asm
LOAD R1, [X]
ADD  R2, R1, 1
ADD  R3, R2, 1
```

If the load incurs a long memory delay:

```text
LOAD delayed
↓
R1 unavailable
↓
first ADD waits
↓
R2 unavailable
↓
second ADD waits
```

The memory hierarchy therefore affects more than the isolated cost of a load. It can delay an entire dependent computation.

An independent instruction may still make progress while the load is outstanding, if the CPU can schedule it.

---
# Memory Latency vs Memory Bandwidth

Two different access structures illustrate different potential limits.

```text
Dependent pointer chasing:
load address → obtain next address → load again
```

Here, each address becomes known only after the preceding load. The chain is strongly sensitive to access latency.

```text
Independent loads:
load A    load B    load C    load D
```

Here, multiple requests may overlap. With enough requests in flight, memory bandwidth may become the limit.

However, independent loads do **not** guarantee bandwidth saturation. The CPU’s ability to maintain requests in flight also matters.

Improving data locality can reduce costly accesses, but performance depends on whether the workload is limited by latency, bandwidth or another mechanism.

---
# Conditional Branches and Prediction

For:

```asm
CMP R1, R2
JNE target
```

execution must eventually follow the architecturally correct path. Waiting for every branch outcome before making further progress could leave resources idle.

**Branch prediction** allows the processor to choose a likely path and begin speculative work before the condition has been resolved.

```text
prediction correct
→ speculative progress can be useful

prediction wrong
→ wrong-path speculative work is discarded
→ resume on correct path
→ extra cost
```

In a conceptual exercise with 1,000 branches and an assumed average penalty of ten cycles per misprediction:

| | Prediction accuracy | Mispredictions | Extra cycles |
|---|---:|---:|---:|
| A | 99% | 10 | 100 |
| B | 60% | 400 | 4,000 |

These figures illustrate the impact of incorrect predictions; real penalties are not universally fixed.

Fewer mispredictions do not, by themselves, prove that an entire program will finish sooner.

---
# Superscalar Execution

A **superscalar** processor can potentially issue multiple instructions during one clock cycle, subject to its resources and dependencies.

```text
one cycle
≠
necessarily one instruction completed
```

This helps explain how aggregate IPC can exceed one on suitable workloads.

Superscalar capability does not guarantee that every workload uses all available execution resources.

---
# Out-of-Order Execution

Consider:

```asm
A: LOAD R1, [X]       ; delayed
B: ADD  R2, R1, 1     ; depends on A
C: ADD  R3, R4, R5    ; independent
```

B cannot obtain its input until A supplies R1. C may be ready immediately.

An out-of-order processor can internally execute C while A remains pending and B waits.

```text
program order: A → B → C

possible internal progress:
A begins
C executes
A produces value
B executes
```

Internal execution can be reordered while required architectural behavior is preserved. Correctness still constrains data and memory dependencies, exceptions and observable effects.

---
# CPI and IPC

**CPI (Cycles Per Instruction)** is the average number of cycles per retired instruction over the measured instruction stream.

**IPC (Instructions Per Cycle)** is the average number of retired instructions per cycle over that stream.

```text
CPI = cycles / instructions
IPC = instructions / cycles

IPC = 1 / CPI
```

The reciprocal relationship applies when both quantities use the same cycle and retired-instruction counts.

For the conceptual CPU comparison:

| | CPU A | CPU B |
|---|---:|---:|
| Instructions | 1 billion | 1 billion |
| Cycles | 2 billion | 1.5 billion |
| CPI | 2 | 1.5 |
| IPC | 0.5 | ≈0.667 |

These are workload-dependent aggregate metrics, not immutable specifications of the processors.

IPC measures observed progress. It does not alone establish *why* one implementation achieves more progress.

---
# A Simplified CPU-Time Model

Under an appropriate constant-frequency approximation:

```text
CPU execution time
≈
retired instructions × average CPI / clock frequency
```

The simplified relationship is useful for decomposing observed execution cost. It is not a complete prediction of wall-clock time in a real system.

For example:

| | Program A | Program B |
|---|---:|---:|
| Instructions | 100 million | 150 million |
| CPI | 3 | 1.5 |
| Total cycles | 300 million | 225 million |

B executes more instructions yet requires 25% fewer cycles.

A lower CPI may reflect greater overlap, fewer delays or a different instruction mix. It is an observation, not an automatic causal diagnosis.

---
# Performance Is Constrained by Bottlenecks

A workload can be limited by different factors at different times:

```text
dependency latency
memory latency
memory bandwidth
branch behavior
instruction throughput
execution-resource capacity
```

Increasing the capacity of a non-limiting resource may yield little improvement.

A useful diagnostic question is:

> What is preventing this workload from completing more useful work right now?

The answer must be investigated, not assumed from a source-code pattern or a single timing result.

---
# Benchmarking Is an Experiment

The Phase 1 workflow is:

```text
prediction
↓
controlled experiment
↓
measurement
↓
repeat
↓
compare
↓
explain
↓
separate evidence from inference
```

A useful benchmark defines the workload, the quantity measured and the hypothesis under test.

Basic hazards include compiler optimization, dead-code elimination, too-short measurements, startup effects, clock-frequency variation, background activity and different instruction sequences.

Multiple runs help reveal variation. Medians are often useful summaries, but repeated timings alone do not isolate a microarchitectural cause.

---
# Practical Experiment — Dependent vs Independent Arithmetic

The learner performed the experiment on an x86-64 Ubuntu machine using:

```text
GCC 13.3.0
GNU objdump 2.42
-O2 compilation
CLOCK_MONOTONIC elapsed-time measurement
```

`perf` was not installed. The experiment did not require it.

The intended workload contained **400 million** updates of:

```c
x = x * 3 + 1;
```

The two arrangements were:

```text
Dependent:
400 million updates along one chain

Independent:
400 million updates distributed across four chains
```

The benchmark used unsigned 64-bit arithmetic; overflow wraps modulo 2^64. The returned results were consumed by the program so that the computations were observable at the C level.

The two functions were not required to return the same number. The experiment compared arithmetic workloads with equal intended update counts, not two implementations of an identical mathematical function.

---
# First Disassembly — The Compiler Preserved Four Chains

With one update per iteration, the dependent implementation contained:

```asm
lea rax,[rax+rax*2+0x1]
sub rdx,0x1
jne ...
```

The independent implementation contained four updates to different registers:

```asm
lea rdi,[rdi+rdi*2+0x1]
lea rax,[rax+rax*2+0x1]
lea rcx,[rcx+rcx*2+0x1]
lea rdx,[rdx+rdx*2+0x1]
```

The first version performed 400 million loop iterations. The second performed 100 million iterations with four updates per iteration.

The different loop-control counts were a confounding factor.

The first measured runs were:

| Run | Dependent (s) | Independent (s) |
|---|---:|---:|
| 1 | 0.180432 | 0.041972 |
| 2 | 0.168271 | 0.041397 |
| 3 | 0.166967 | 0.042542 |
| 4 | 0.168562 | 0.042001 |
| 5 | 0.166441 | 0.041715 |

The median times were approximately 0.1683 s and 0.0420 s, a ratio of approximately **4.01×**.

This supported the overlap hypothesis but did not isolate it, because the loops had different structures.

---
# Controlling the Loop Structure Revealed Another Compiler Effect

The dependent C loop was changed to run `N / 4` iterations, with four consecutive updates per iteration:

```c
for (uint64_t i = 0; i < N / 4; i++) {
    x = x * 3 + 1;
    x = x * 3 + 1;
    x = x * 3 + 1;
    x = x * 3 + 1;
}
```

GCC optimized those four source-level updates into two instructions:

```asm
lea rax,[rax+rax*8]
lea rax,[rax+rax*8+0x28]
```

Together these implement:

```text
x → 9x → 81x + 40
```

Four successive applications of `x = 3x + 1` also yield `81x + 40` modulo 2^64.

The compiler preserved the result, but **changed the executed arithmetic instruction count and dependency chain**.

This made an ordinary optimized-C comparison inadequate for isolating the intended instruction structure.

---
# Controlled Assembly Experiment

GCC inline assembly was used to retain four intended x86-64 `LEA` instructions per loop iteration.

The dependent loop contained:

```asm
lea rax,[rax+rax*2+0x1]
lea rax,[rax+rax*2+0x1]
lea rax,[rax+rax*2+0x1]
lea rax,[rax+rax*2+0x1]
```

Each update needed the previous `rax` value.

The independent loop contained:

```asm
lea rdi,[rdi+rdi*2+0x1]
lea rsi,[rsi+rsi*2+0x1]
lea rcx,[rcx+rcx*2+0x1]
lea rax,[rax+rax*2+0x1]
```

These updates used separate registers.

Both loops executed 100 million iterations and four arithmetic `LEA` instructions per iteration.

The independent version also contained additional register moves, so the machine-code workloads were **not perfectly identical apart from dependencies**. Both experiments had branch and loop overhead. The new design nevertheless controlled the main earlier differences more closely.

---
# Controlled Benchmark Results

The learner recorded five runs:

| Run | Dependent (s) | Independent (s) |
|---|---:|---:|
| 1 | 0.175568 | 0.044495 |
| 2 | 0.169200 | 0.044792 |
| 3 | 0.169233 | 0.044788 |
| 4 | 0.169701 | 0.044347 |
| 5 | 0.166902 | 0.046859 |

Summary:

| Metric | Dependent | Independent |
|---|---:|---:|
| Median elapsed time | 0.169233 s | 0.044788 s |
| Minimum | 0.166902 s | 0.044347 s |
| Maximum | 0.175568 s | 0.046859 s |

The ratio of median times was approximately **3.78×**.

The observed advantage remained large after controlling the number of arithmetic `LEA` instructions and loop iterations.

**Observation:** the independent-chain implementation completed this benchmark much sooner.

**Supported interpretation:** the result is consistent with a CPU exploiting available independent arithmetic operations, while the dependent chain constrains progress.

**Not established by timing alone:** the exact contribution of each execution resource, the CPU’s internal scheduling behavior or the fraction of improvement attributable solely to ILP. Hardware counters and further experiments could strengthen that attribution.

This distinction between evidence and inference is as important as the speedup itself.

# Prediction, Experiment, Observation, Explanation

The practical investigation proceeded through several revisions rather than treating the first result as proof.

```text
prediction:
independent arithmetic chains should expose more opportunities for overlap

experiment:
compare one long chain with four independent chains

initial observation:
approximately 4.01× median elapsed-time ratio

problem found:
different loop iteration counts

revision:
equalize iteration counts

new problem found:

revision:

controlled observation:
approximately 3.78× median elapsed-time ratio

interpretation:

```

The experiment illustrates why generated machine code must be inspected whenever a compiler transformation could invalidate the intended comparison.

---
# Algorithmic Complexity vs Machine Execution Cost

Algorithmic complexity describes how resource requirements grow with input size; measured runtime also depends on machine-level effects.

An `O(n log n)` algorithm with favorable locality can outperform an `O(n)` algorithm that performs expensive scattered memory accesses for a particular input size.

This does not mean the asymptotic comparison is wrong. It means asymptotic growth and practical execution cost answer different questions.

```text
algorithmic complexity
→ growth of required work

machine performance
→ cost of executing that work on a particular system
```

Neither perspective replaces the other.

---
# Optimizing the Relevant Bottleneck

Amdahl’s law provides a useful intuition: accelerating one component can improve total execution time only in proportion to the time that component originally consumed.

In the assessment, a program took 200 ms and a targeted function accounted for 5% of that time:

```text
original function time = 10 ms
unaffected work       = 190 ms
```

Making the function ten times faster yields:

```text
new function time = 1 ms
new total time    = 191 ms
```

The overall reduction is **4.5%**, even though the isolated function is ten times faster.

The broader lesson is not to optimize what merely looks inefficient. Profile first, then target the cost that matters.

---
# Compiler, ISA, Microarchitecture and Workload

Performance explanations need the correct abstraction level.

```text
source program
↓
compiler chooses machine-code sequence
↓
ISA defines required instruction semantics
↓
microarchitecture executes the instructions
↓
workload, memory state and system conditions influence observed cost
```

The ISA defines correctness requirements, not a universal fixed latency for each instruction.

The compiler can change instruction count and dependencies, as observed when four arithmetic source updates became two `LEA` instructions.

A microarchitecture can exploit independent operations and overlap internal work while preserving architecturally required behavior.

The workload determines which dependencies, accesses and branches occur. Measurements are necessary to determine their actual importance.

---
# Production Systems Perspective

The same reasoning applies beyond synthetic CPU loops.

A game loop can be latency-sensitive because the time required to complete each frame affects responsiveness and frame rate.

A data-processing system may be throughput-sensitive because it must complete large quantities of work per second.

A database or storage engine may be constrained by access patterns, memory availability or I/O rather than arithmetic throughput.

Optimizing a workload can move the bottleneck elsewhere. A faster computation may expose memory transfer as the new dominant limit.

Small benchmarks help isolate mechanisms. They do not automatically predict production behavior.

# Core Mental Model

When investigating performance, ask:

```text
What useful work is required?

What exactly is being measured?

Which operations depend on earlier results?

Which operations can overlap?

What data must become available?

Where is the data likely to be found?

Does control flow create uncertainty?

What execution resources can limit progress?

Did the compiler change the actual instruction sequence?

What did the benchmark observe?

What explanations remain hypotheses?

Which optimization targets the measured bottleneck?
```

The durable model is:

```text
workload
+
compiler-generated instructions
+
dependencies
+
memory behavior
+
control flow
+
available overlap
+
microarchitecture
+
measurement conditions
↓
observed performance
```

# Final Takeaway

Performance is not simply instruction count multiplied by a universal instruction cost.

Instructions can depend on one another. Independent work can overlap. Memory accesses can delay dependent work. Branch predictions can maintain progress or incur recovery costs. Compiler transformations can change the instructions that execute. Different microarchitectures can realize the same ISA-defined behavior at different rates.

CPI, IPC and elapsed time describe aspects of the result, but they do not automatically identify its cause.

The essential engineering discipline is:

> Define the useful work, measure its cost, identify what constrains progress, test a specific explanation, and verify that an optimization improves the workload that matters.
