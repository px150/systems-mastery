# Systems Mastery 1.3 — Memory Hierarchy

> Memory performance depends not only on how much data a program accesses, but on where that data is located and how predictably it is accessed.

---

# Objective

The previous module established a CPU model based on architectural state and ISA-defined state transformations.

Instructions operate on registers and can transfer data between registers and memory.

But this simplified model hides an important systems problem.

Memory cannot simultaneously maximize:

```text
speed
+
capacity
+
low cost
+
persistence
```

Fast storage close to the processor is expensive and limited.

Large storage can hold much more data, but is slower.

Persistent storage preserves information without power, but operates on a very different performance scale from CPU-local storage.

Modern systems therefore organize storage as a hierarchy.

Conceptually:

```text
registers
    ↓
L1 cache
    ↓
L2 cache
    ↓
L3 cache
    ↓
RAM
    ↓
persistent storage
```

This module asks the next systems question:

> How does the organization and access pattern of data affect the real cost of memory operations?

The purpose is not to memorize the exact cache sizes or timings of a particular processor.

The purpose is to construct a systems-level mental model involving:

```text
memory hierarchy
+
locality
+
cache lines
+
hits and misses
+
latency
+
bandwidth
+
working sets
+
access patterns
```

and to understand why two algorithms with the same asymptotic complexity can behave very differently on real hardware.

---

# Why a Memory Hierarchy Exists

Registers provide extremely fast storage directly available to processor instructions.

But a computer cannot simply replace all other storage with millions or billions of registers.

Larger storage structures require more hardware resources and cannot preserve the same combination of access speed, physical proximity and cost.

At the same time, programs require far more storage than registers can provide.

This creates a fundamental trade-off.

Conceptually:

```text
faster
smaller
more expensive per byte
closer to CPU
        ↑
        │
registers
cache
RAM
persistent storage
        │
        ↓
slower
larger
cheaper per byte
farther from CPU
```

No single storage technology simultaneously provides every desirable property.

The system therefore combines several levels.

---

# The Fundamental Trade-Off

Memory technologies can be evaluated along several dimensions.

Important ones include:

```text
speed
capacity
cost
persistence
```

A storage level optimized for one property may sacrifice another.

Registers are extremely fast but extremely limited.

Caches are larger than registers but still relatively small.

RAM provides much greater capacity but higher access cost.

Persistent storage provides large capacity and retains data without power, but is substantially slower than processor-local storage.

The hierarchy exists because the machine needs all of these properties.

---

# Registers and Cache

Registers and caches both provide storage close to computation, but they play different roles.

Registers are part of the processor's architectural model.

Instructions can explicitly refer to architectural registers.

For example:

```text
ADD R2, R0, R1
```

identifies registers directly.

Cache is different.

A normal program does not generally issue instructions such as:

```text
put this value in L1
```

Instead, caches are primarily managed by the processor's microarchitecture.

They attempt to keep useful data close to the CPU automatically.

This distinction connects directly to the previous module:

```text
registers
→ architectural state

cache
→ microarchitectural mechanism
```

---

# The Cache Idea

Suppose a program repeatedly accesses data from RAM.

Without an intermediate storage level:

```text
CPU
 ↓
RAM
 ↓
CPU
```

every access would potentially require paying the higher cost of reaching main memory.

But programs often reuse data.

If recently used data is retained in a smaller, faster storage area near the processor:

```text
CPU
 ↓
cache
 ↓
RAM
```

future accesses may be satisfied without returning to RAM.

This is the fundamental role of cache.

> Cache exploits patterns in program behavior to reduce the effective cost of memory access.

---

# Locality

Caches are useful because programs often exhibit:

```text
locality
```

Two particularly important forms are:

```text
temporal locality
spatial locality
```

These describe different reasons why recently accessed memory may be useful again.

---

# Temporal Locality

Temporal locality means that recently accessed data is likely to be accessed again soon.

Suppose execution repeatedly uses:

```text
A
B
A
C
A
```

The value associated with:

```text
A
```

has strong temporal locality.

Keeping it near the CPU is useful because the cost of retrieving it from a slower level does not need to be paid every time.

Conceptually:

```text
recently used
      ↓
likely useful again soon
      ↓
keep nearby
```

Temporal locality is therefore locality across time.

---

# Spatial Locality

Spatial locality means that after accessing one memory location, nearby locations are likely to be accessed soon.

Consider an array:

```text
A[0]
A[1]
A[2]
A[3]
```

If its elements are contiguous in memory, accessing:

```text
A[0]
```

makes nearby data potentially useful.

Conceptually:

```text
address 1000
address 1004
address 1008
address 1012
```

A sequential traversal naturally exhibits spatial locality.

This suggests that moving only the exact requested byte or value may waste an opportunity.

The system can instead move a block of nearby memory.

---

# Cache Lines

Caches typically transfer memory in blocks called:

```text
cache lines
```

If one address is requested, the processor may bring a whole neighboring region into cache.

Conceptually:

```text
requested value
      ↓

[ A ][ B ][ C ][ D ][ E ][ F ] ...
  ↑
requested

      ↓

[--------- cache line ---------]
```

The exact cache-line size is an implementation property and should not be assumed universally.

On the tested machine:

```bash
getconf LEVEL1_DCACHE_LINESIZE
```

produced:

```text
64
```

The observed L1 data-cache line therefore contained:

```text
64 bytes
```

On a system where:

```text
sizeof(int) = 4 bytes
```

one 64-byte line can contain:

```text
64 / 4 = 16 ints
```

This makes sequential traversal particularly effective.

One fetched line may serve many subsequent accesses.

---

# Cache Hits

Suppose:

```text
A[0]
```

causes a cache line containing:

```text
A[0] ... A[15]
```

to be fetched.

A later access to:

```text
A[1]
```

may already find the required data in cache.

This is a:

```text
cache hit
```

Conceptually:

```text
requested address
      ↓
cache contains it?
      ↓
     yes
      ↓
cache hit
```

The access can then be satisfied from the nearby cache level.

---

# Cache Misses

If the requested data is not present in a cache level:

```text
requested address
      ↓
cache contains it?
      ↓
      no
      ↓
cache miss
```

the system must look farther down the hierarchy.

Conceptually:

```text
L1 miss
   ↓
L2
   ↓
L3
   ↓
RAM
```

A miss therefore does not mean the data does not exist.

It means that the requested data was not found at that particular cache level.

---

# Multiple Cache Levels

A single enormous cache would recreate many of the physical and performance problems that motivated the hierarchy.

Modern processors therefore commonly use multiple cache levels.

Conceptually:

```text
CPU
 ↓
L1
 ↓
L2
 ↓
L3
 ↓
RAM
```

The levels trade capacity for proximity and speed.

Broadly:

```text
L1
→ smallest and closest

L2
→ larger

L3
→ larger again

RAM
→ much larger and farther from CPU execution
```

The exact organization is processor-specific.

The conceptual model matters more than memorizing one processor's topology.

---

# Observing the Cache Hierarchy

The cache hierarchy of the tested Linux machine was inspected with `lscpu`.

The machine reported:

```text
L1d cache: 480 KiB (10 instances)
L1i cache: 320 KiB (10 instances)
L2 cache: 12.5 MiB (10 instances)
L3 cache: 24 MiB (1 instance)
```

`L1d` represents L1 data cache.

`L1i` represents L1 instruction cache.

The totals reported by `lscpu` are aggregated across cache instances.

For the observed machine:

```text
L1d:
480 KiB / 10
= 48 KiB per instance

L2:
12.5 MiB / 10
= 1.25 MiB per instance

L3:
24 MiB / 1
= 24 MiB
```

This produces an approximate observed hierarchy:

```text
L1d   ~48 KiB per instance
L2    ~1.25 MiB per instance
L3    ~24 MiB shared instance
```

The experiment also illustrates why cache topology should not be reduced to an overly simplistic universal diagram.

The hierarchy model is useful.

Its exact physical organization remains microarchitecture-specific.

---

# RAM

RAM provides the main working memory available to running software.

Compared with caches, RAM offers much greater capacity.

But accessing it has a higher cost than finding the same data in a nearby cache.

Conceptually:

```text
CPU needs data
      ↓
cache hit
→ nearby data

cache miss
      ↓
RAM
→ higher access cost
```

RAM is also volatile.

Its contents do not provide persistent storage across power loss.

---

# Persistent Storage

Persistent storage includes technologies such as:

```text
SSD
HDD
```

Its defining role is different from that of cache or RAM.

Persistent storage retains information when the machine is powered off.

Conceptually:

```text
registers  → volatile
cache      → volatile
RAM        → volatile
SSD / HDD  → persistent
```

Persistent storage therefore solves a different systems problem.

It is not simply another CPU cache level.

Files, applications and long-lived data can survive across executions because they are stored persistently.

---

# Latency

Latency describes the delay associated with completing an operation.

For memory, the relevant question is conceptually:

> How long does it take before the requested data becomes available?

A hierarchy exists partly because different storage levels have very different access costs.

Conceptually:

```text
request
   ↓
waiting
   ↓
data available
```

The duration of that delay is related to latency.

Lower latency is particularly important when execution depends on the result before useful work can continue.

---

# Bandwidth

Bandwidth describes how much data can be transferred per unit of time.

Conceptually:

```text
bytes transferred
-----------------
      time
```

Latency and bandwidth are different properties.

A system may have:

```text
low latency
lower bandwidth
```

while another may have:

```text
higher latency
higher bandwidth
```

For large sequential transfers, bandwidth can dominate because the initial access cost is amortized across a large amount of data.

For small or dependent accesses, latency can become much more important.

---

# Latency vs Bandwidth

Suppose:

```text
System A:
latency = 2 s
bandwidth = 1 GB/s

System B:
latency = 1 s
bandwidth = 100 MB/s
```

For a tiny transfer, the lower latency of B may matter greatly.

For a 10 GB sequential transfer, A's much greater bandwidth can dominate the total execution time.

This establishes an important principle:

> Memory performance cannot be described by a single notion of "speed."

Both latency and bandwidth matter, and their importance depends on the workload.

---

# Arrays and Spatial Locality

Arrays naturally expose a memory layout favorable to spatial locality.

Conceptually:

```text
A[0] A[1] A[2] A[3] A[4]
```

may occupy:

```text
1000
1004
1008
1012
1016
```

for 4-byte elements.

Sequential iteration:

```c
for (size_t i = 0; i < n; i++) {
    use(array[i]);
}
```

therefore accesses predictable neighboring addresses.

A cache line fetched for one element may contain several future elements.

This allows the cost of fetching the line to be amortized across multiple useful accesses.

---

# Linked Structures

Linked structures can behave differently.

Consider:

```text
node A
  ↓
node B
  ↓
node C
  ↓
node D
```

The logical relationship does not require the nodes to occupy adjacent memory.

They may instead be located at:

```text
A → 0x1000
B → 0x9F20
C → 0x3410
D → 0xB800
```

Traversing the structure may therefore access memory locations that are physically far apart.

This reduces spatial locality.

There is also another problem.

To discover the location of `B`, execution may first need to read the pointer stored in `A`.

To discover `C`, it must first read `B`.

Conceptually:

```text
A
↓ read pointer
B
↓ read pointer
C
↓ read pointer
D
```

This dependency pattern is commonly described as:

```text
pointer chasing
```

The next address may not be known until the previous memory access completes.

This makes it harder for the processor to anticipate future accesses.

---

# Prefetching

Modern processors may attempt to predict future memory accesses and retrieve data before it is explicitly needed.

This is:

```text
prefetching
```

Regular patterns are easier to anticipate.

For example:

```text
1000
1004
1008
1012
1016
```

provides a predictable sequence.

A linked structure may instead produce:

```text
1000
9F20
3410
B800
```

where the next address depends on data obtained from the current node.

Prefetching is a microarchitectural mechanism.

Software does not need to explicitly request ordinary hardware prefetching for it to influence performance.

---

# Complexity Does Not Describe Memory Behavior

Consider two algorithms that both process:

```text
n elements
```

Both may therefore have:

```text
O(n)
```

time complexity.

But Big-O does not describe:

```text
cache locality
cache misses
memory latency
bandwidth utilization
prefetchability
pointer dependencies
```

Two `O(n)` algorithms may consequently have very different real execution times.

For example:

```text
Algorithm A:
sequential array traversal

Algorithm B:
scattered pointer traversal
```

Both can perform linear work.

But their memory behavior may differ substantially.

This establishes a broader systems principle:

> Asymptotic complexity describes growth of computational work, not the complete cost of executing that work on real hardware.

---

# Working Set

A program may allocate a large amount of memory while actively using only a small portion of it.

Suppose a process allocates:

```text
2 GiB
```

but repeatedly operates on the same:

```text
20 KiB
```

The smaller active region is more relevant to cache behavior than the total allocation.

This actively used data is part of the program's:

```text
working set
```

Conceptually:

```text
total allocated memory
┌───────────────────────────────────────────────┐
│                                               │
│     ┌──────────────┐                          │
│     │ working set  │                          │
│     └──────────────┘                          │
│                                               │
└───────────────────────────────────────────────┘
```

If the working set fits comfortably within a cache level, repeated accesses may frequently be served from that level.

If it exceeds cache capacity, more data must move through slower levels of the hierarchy.

---

# Architectural vs Microarchitectural Behavior

Consider an architectural operation:

```text
LOAD R0, [A]
```

The ISA defines the required architectural result.

Conceptually:

```text
R0 ← memory[A]
```

Suppose one execution finds the required data in L1.

Another reaches RAM.

The architectural result is still the same:

```text
R0 contains memory[A]
```

What changes is the internal cost of producing that result.

Therefore:

```text
ISA
→ defines the visible result
```

while:

```text
microarchitecture
→ determines how the processor realizes that result
```

Caches belong to the second category.

This extends the architecture/microarchitecture distinction established in the previous module.

---

# The Hierarchy as an Abstraction

At the architectural level, software can reason about memory as though an address identifies a value.

Conceptually:

```text
LOAD R0, [A]
```

does not require the programmer to specify:

```text
check L1
check L2
check L3
access RAM
```

The hardware handles these mechanisms.

The hierarchy therefore hides substantial implementation complexity.

But abstraction does not eliminate cost.

Two architecturally equivalent loads may have very different performance depending on where the requested data is found.

This is a recurring systems principle:

> An abstraction can hide mechanism without eliminating the performance consequences of that mechanism.

---

# Access Pattern Experiment

A C benchmark was created to compare:

```text
sequential access
```

with:

```text
strided access
```

over a data set intentionally much larger than the observed CPU caches.

The allocation contained:

```text
64 × 1024 × 1024 ints
```

With 4-byte integers:

```text
≈ 256 MiB
```

This exceeds the observed:

```text
24 MiB L3
```

by a large margin.

---

# Sequential Access Pattern

The sequential experiment accessed:

```text
array[0]
array[1]
array[2]
array[3]
...
```

With 4-byte integers and a 64-byte cache line, one line can contain approximately:

```text
16 ints
```

The traversal can therefore consume many useful values from each fetched line.

Conceptually:

```text
cache line
┌──────────────────────────────────────────────┐
│ 0 │ 1 │ 2 │ 3 │ ... │ 14 │ 15              │
└──────────────────────────────────────────────┘
  ↑   ↑   ↑   ↑         ↑    ↑
          useful accesses
```

---

# Strided Access Pattern

The strided experiment used:

```text
STRIDE = 16
```

and therefore accessed:

```text
array[0]
array[16]
array[32]
array[48]
...
```

With 4-byte integers:

```text
16 × 4 bytes = 64 bytes
```

Each access therefore moves approximately one cache-line distance forward.

Conceptually:

```text
line 0        line 1        line 2
  ↓             ↓             ↓
[0 ... 15]   [16 ... 31]   [32 ... 47]
 ↑             ↑             ↑
used          used          used
```

Compared with sequential traversal, much less useful data is consumed from each fetched cache line.

---

# Normalizing the Benchmark

Simply comparing total execution time would be misleading.

The basic strided loop touches only one element out of every sixteen.

It would therefore perform fewer accesses than the sequential loop.

The experiment compensated by running the strided traversal more times.

Conceptually:

```text
sequential accesses
≈
strided accesses
```

The result was then normalized as:

```text
total time
----------
accesses
```

and reported as:

```text
ns/access
```

This value represents average benchmark throughput.

It must not be interpreted as the physical latency of one individual RAM access.

---

# Access Pattern Results

The tested machine produced:

```text
=== Access pattern ===
Sequential: 0.224 s, 0.33 ns/access
Stride 16:  1.819 s, 2.71 ns/access
```

The strided access therefore cost approximately:

```text
2.71 / 0.33
≈ 8.2×
```

as much per useful access in this run.

The important observation is not the exact ratio.

The important observation is:

```text
same broad algorithmic task
+
different memory access pattern
=
substantially different execution cost
```

The result strongly demonstrates the practical importance of spatial locality and cache-line utilization.

# Working-Set Experiment

A second experiment varied the size of the actively traversed data while keeping the total amount of useful data read approximately constant.

The tested working sets were:

```text
16 KiB
256 KiB
2 MiB
32 MiB
100 MiB
```

These were chosen relative to the observed cache capacities:

```text
L1d   ~48 KiB
L2    ~1.25 MiB
L3    ~24 MiB
```

The experiment therefore included working sets:

```text
below L1 capacity
above L1
above L2
above L3
far above L3
```

The prediction was that larger working sets would eventually increase average access cost as they stopped fitting comfortably in nearby cache levels.

---

# Working-Set Results

The tested machine produced:

```text
=== Working set ===
16 KiB : 0.23 ns/access
256 KiB: 0.23 ns/access
2 MiB  : 0.24 ns/access
32 MiB : 0.31 ns/access
100 MiB: 0.33 ns/access
```

The result did not produce clean steps corresponding exactly to:

```text
L1
↓
L2
↓
L3
↓
RAM
```

Instead, the cost remained nearly constant through:

```text
16 KiB
256 KiB
2 MiB
```

and increased more visibly at:

```text
32 MiB
100 MiB
```

Notably:

```text
32 MiB > observed 24 MiB L3
```

The experiment therefore showed the expected broad trend without implying that nominal cache boundaries translate directly into simple timing boundaries.

---

# Why Cache Boundaries Are Not Perfect Timing Steps

Real processors contain mechanisms that make memory behavior more complicated than:

```text
fits in L1 → timing A
fits in L2 → timing B
fits in L3 → timing C
otherwise   → timing D
```

Observed performance may also be influenced by:

```text
prefetching
memory-level parallelism
compiler optimization
instruction scheduling
cache organization
replacement behavior
bandwidth
other microarchitectural effects
```

The benchmark therefore should not be used to derive statements such as:

```text
L1 latency = 0.23 ns
RAM latency = 0.33 ns
```

That interpretation would be incorrect.

The measured values are average throughput-oriented results for these particular loops on this particular machine.

# Memory Hierarchy and Data Structures

The data structures studied previously now acquire a hardware dimension.

An array provides:

```text
contiguous layout
+
predictable traversal
+
spatial locality
+
prefetch opportunities
```

A linked structure may provide:

```text
scattered layout
+
pointer dependencies
+
weaker spatial locality
+
less predictable future addresses
```

This does not make linked structures inherently bad.

Their value depends on the operations and constraints required by the problem.

But algorithmic reasoning should now include both:

```text
abstract operation cost
```

and:

```text
memory behavior
```

when real performance matters.

---

# Core Mental Model

When reasoning about memory performance, ask:

```text
Where is the data likely to be?

How large is the active working set?

Are accesses sequential or scattered?

Does the program exhibit temporal locality?

Does it exhibit spatial locality?

How much useful data is consumed from each cache line?

Can future accesses be predicted?

Are accesses dependent on previous memory results?

Is the workload latency-sensitive or bandwidth-sensitive?

Am I reasoning about an architectural guarantee
or a microarchitectural implementation detail?

Am I confusing Big-O complexity with real execution cost?
```

The useful abstraction is:

```text
program memory accesses
        ↓
access pattern
        +
working set
        ↓
memory hierarchy
        ↓
data movement
        ↓
observed execution cost
```

The processor attempts to keep useful data close to execution.

Locality makes that strategy effective.

Cache lines exploit spatial locality.

Multiple cache levels balance speed and capacity.

RAM provides much larger volatile storage.

Persistent storage preserves data across power loss.

The microarchitecture manages much of this hierarchy automatically.

The central principle is:

> Memory is not uniformly expensive: real access cost depends on where data is found, how much data is active, and how predictably the program accesses it.

# Final Takeaway

A program may conceptually access memory through simple addresses.

The underlying machine does something more complex.

Data moves through a hierarchy:

```text
registers
    ↓
L1
    ↓
L2
    ↓
L3
    ↓
RAM
    ↓
persistent storage
```

The hierarchy exists because no single storage level can simultaneously provide maximum speed, capacity, low cost and persistence.

Caches exploit program locality.

Temporal locality makes recently used data valuable.

Spatial locality makes nearby data valuable.

Cache lines move blocks rather than isolated values.

Working-set size determines how much actively used data can remain in nearby storage.

Access patterns determine how effectively those transferred blocks are used.

Therefore two algorithms with identical:

```text
O(n)
```

complexity may have very different real costs.

At the systems level:

```text
algorithm
    ↓
data layout
    +
access pattern
    ↓
working set
    ↓
memory hierarchy
    ↓
data movement
    ↓
real execution cost
```

The essential model is:

> Memory access is not uniformly expensive. Performance depends on locality, working-set size, access pattern and where the required data is found in the hierarchy.
