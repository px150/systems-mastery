# Systems Mastery 1.4 — Instruction Execution

> A running program is a continuing sequence of architectural state transformations driven by instruction encodings, operand availability and control-flow decisions.

---

# Objective

The previous modules established three important ideas.

Binary Representation established that bits acquire meaning only through an interpretation contract.

CPU Architecture established that a processor can be modeled as a machine whose instructions transform architectural state.

Memory Hierarchy established that information required by computation must become available to the processor, and that the cost of obtaining it depends on where it is found.

Instruction Execution connects these ideas.

Suppose the architectural state contains:

```text
R0 = 5
R1 = 7
R2 = 0

PC = 0x1000
```

and memory beginning at:

```text
0x1000
```

contains the bytes encoding the next machine instruction.

The architectural model from the previous module allowed reasoning in terms of:

```text
state before
↓
instruction
↓
state after
```

But this hides an important question:

> What must actually happen between those two architectural states?

The purpose of this module is to unpack that transition.

Conceptually:

```text
Program Counter
↓
instruction bytes become available
↓
instruction is interpreted according to the ISA
↓
required operands are identified
↓
operands become available
↓
required operation occurs
↓
architectural state changes
↓
next Program Counter value is determined
```

The goal is not to memorize a three-box fetch-decode-execute diagram.

The goal is to understand why each part of instruction execution is necessary.

---

# The Program Counter Identifies the Next Instruction

The Program Counter does not contain the instruction itself.

It contains an address identifying where the next instruction begins.

For example:

```text
PC = 0x1000
```

means conceptually:

```text
next instruction begins at address 0x1000
```

The processor still needs the bytes stored at that location before it can determine what operation they represent.

Therefore:

```text
PC
↓
instruction address
↓
instruction bytes
```

The Program Counter provides location.

It does not by itself provide meaning.

---

# Obtaining Instruction Bytes

Machine instructions exist as encoded bits stored in memory.

If the Program Counter identifies the beginning of the next instruction, those bytes must become available to the processor before the instruction can affect architectural state.

Conceptually:

```text
PC
↓
instruction address
↓
memory hierarchy
↓
instruction bytes
```

This reconnects instruction execution directly to Memory Hierarchy.

Instruction retrieval itself requires information movement.

The processor cannot interpret an instruction whose bytes have not yet become available.

---

# Instruction Bytes Need Interpretation

Obtaining instruction bytes is not enough.

A sequence of bits has no useful instructional meaning without an interpretation contract.

Binary Representation established:

```text
bits
+
interpretation
=
meaning
```

For machine instructions, that interpretation contract is provided by the ISA.

Conceptually:

```text
instruction bits
+
ISA
=
architectural operation
```

The processor therefore interprets the retrieved encoding according to the ISA.

This is instruction decoding at the conceptual level.

```text
instruction bits
↓
ISA interpretation
↓
operation + operand information
```

The ISA determines what the encoding means.

Decoding does not assign arbitrary meaning to the bits.

---

# Instruction Decoding

Consider a conceptual instruction:

```text
ADD R2, R0, R1
```

After decoding, the processor must know at least:

```text
operation:
ADD

sources:
R0
R1

destination:
R2
```

This still does not complete the instruction.

Knowing which operation is required does not mean that the required inputs are already available.

The operands must also be obtained.

---

# Operand Acquisition

Consider:

```text
ADD R2, R0, R1
```

Before the addition can produce a result, the values stored in:

```text
R0
R1
```

must be available to the execution mechanism.

Conceptually:

```text
decode ADD
↓
identify R0 and R1
↓
read R0
↓
read R1
↓
perform addition
↓
write R2
```

Operand acquisition is therefore a separate conceptual requirement from identifying the operation itself.

---

# Register Operands

Register operands are already part of architectural processor state.

For:

```text
ADD R2, R0, R1
```

the required input values can be obtained directly from registers.

No data-memory access is inherently required to obtain those operands.

Conceptually:

```text
R0
+
R1
↓
operation
↓
R2
```

This distinction becomes important when compared with memory operands.

---

# Immediate Operands

An instruction may also encode a value directly.

For example:

```text
ADD R0, 5
```

Here:

```text
R0
```

is a register operand, while:

```text
5
```

is an immediate operand.

The value is encoded as part of the instruction rather than obtained from a separate memory location.

This gives three important conceptual operand sources:

```text
register
immediate
memory
```

---

# Memory Operands

Consider:

```text
LOAD R0, [A]
```

The required value is not already contained in a register and is not encoded directly in the instruction.

The processor must obtain the value associated with memory address `A`.

Conceptually:

```text
decode LOAD
↓
determine address A
↓
request data
↓
memory hierarchy supplies data
↓
write result into R0
```

This creates an additional dependency.

The instruction cannot complete its architectural effect until the required memory value becomes available.

---

# Loads

A load transfers information conceptually from memory into processor state.

For:

```text
LOAD R0, [A]
```

the required architectural result is:

```text
R0 ← memory[A]
```

The ISA defines what result the instruction must produce.

The memory hierarchy influences how costly obtaining that value may be.

The same architectural result may therefore be produced whether the data is found in:

```text
L1
L2
L3
RAM
```

The observable semantics remain the same.

The internal cost may differ substantially.

---

# Stores

A store moves information in the opposite direction.

For:

```text
STORE [A], R0
```

the value in `R0` must be written to memory location `A`.

Conceptually:

```text
R0
↓
value to store
↓
address A
↓
memory[A]
```

The resulting architectural state includes:

```text
memory[A] = value previously contained in R0
```

A store therefore modifies architectural memory state.

---

# Instruction Access vs Data Access

Instruction execution may involve two different kinds of memory-related activity.

Consider:

```text
mov -0x4(%rbp), %edx
```

The processor first requires the bytes encoding the `mov` instruction.

It then requires the data stored at the memory operand.

Conceptually:

```text
instruction access
→ obtain the instruction itself

data access
→ obtain a memory operand required by the instruction
```

These should not be confused.

For an instruction such as:

```text
add %edx, %eax
```

the operand values may already exist entirely in registers.

A separate data-memory access is therefore not inherently necessary for the addition itself.

Instruction bytes still have to become available.

---

# Execution Is Broader Than the ALU

Arithmetic instructions may naturally involve the ALU.

Examples include:

```text
ADD
SUB
AND
OR
SHIFT
```

But instruction execution cannot be reduced to:

```text
execute
=
ALU operation
```

Instructions may instead involve:

```text
register movement
memory access
address calculation
flag changes
control-flow changes
```

For example:

```text
RET
```

primarily affects control flow.

Its important architectural effect is not an arithmetic result.

Execution therefore means performing or coordinating whatever state transformation the instruction requires.

---

# Architectural State Changes

An instruction transforms some subset of architectural state.

Consider:

```text
ADD R2, R0, R1
```

with:

```text
R0 = 5
R1 = 7
R2 = 0
```

After execution:

```text
R2 = 12
```

while `R0` and `R1` may remain unchanged.

The instruction also affects control progression by causing execution to continue from another instruction address.

This gives the deeper model:

```text
architectural state before
↓
instruction execution
↓
architectural state after
```

where the changed state may include:

```text
registers
flags
memory
Program Counter
```

depending on the instruction.

---

# Sequential Execution

Suppose execution is currently at:

```text
PC = 100
```

and the current instruction occupies four bytes.

If no control-flow instruction changes the path, the next instruction may begin at:

```text
104
```

Conceptually:

```text
current instruction address
+
instruction length
=
next sequential instruction address
```

The Program Counter is updated accordingly.

However, instruction lengths are not universally fixed.

Different ISAs encode instructions differently.

Some use fixed-width encodings.

Others allow variable-length instructions.

Sequential execution therefore requires determining where the current instruction ends and where the next one begins.

---

# Observing Variable-Length Instructions

The tested x86-64 machine provided a direct example.

A function began with instructions at offsets:

```text
+0
+4
+5
+8
+11
+14
+17
+20
+22
+23
```

The first observed instruction was:

```asm
endbr64
```

At:

```text
RIP = ...5129
```

After executing exactly one machine instruction with GDB:

```text
RIP = ...512d
```

The instruction therefore occupied four bytes.

The next instruction occupied only one byte.

This experimentally confirmed that x86-64 instructions do not all have the same length.

---

# Control Flow Changes the Program Counter

Sequential progression is not the only possible behavior.

Consider:

```text
JMP 200
```

The essential architectural effect is:

```text
PC ← 200
```

The processor does not continue to the next sequential instruction.

Instead, execution continues from the target.

This establishes a central principle:

> Control flow is ultimately about determining the address of the next instruction.

---

# Conditional Branches

Conditional branches make the next Program Counter depend on architectural state.

Consider:

```text
CMP R0, R1
JZ target
```

The comparison may update condition flags.

The branch then inspects the relevant condition.

Conceptually:

```text
comparison
↓
flags
↓
conditional branch
↓
choose next PC
```

If the condition is satisfied:

```text
PC ← target
```

Otherwise:

```text
PC ← next sequential instruction
```

---

# Observing a Real Conditional Branch

The following C function was compiled without optimization:

```c
int choose(int a) {
    if (a == 5)
        return 10;

    return 20;
}
```

The resulting relevant x86-64 instructions included:

```asm
cmpl   $0x5,-0x4(%rbp)
jne    <target>
```

For:

```text
a = 5
```

GDB showed:

```text
eflags = ... [ ZF ... ]
```

meaning:

```text
ZF = 1
```

The subsequent:

```asm
jne
```

was therefore not taken.

`RIP` advanced to the next sequential instruction.

When reasoning about:

```text
a = 6
```

the prediction was:

```text
ZF = 0
```

and therefore:

```text
jne
→ branch taken
```

This demonstrates the relationship:

```text
comparison
→ changes flags

conditional branch
→ reads flags

branch result
→ determines next RIP
```

---

# Jumps vs Conditional Branches

An unconditional jump directly selects another instruction address.

```text
JMP target
↓
PC ← target
```

A conditional branch chooses between alternatives.

```text
condition true
→ PC ← target

condition false
→ PC ← sequential address
```

Flags therefore matter for conditional branches.

They are not required merely because an unconditional jump occurs.

---

# Function Calls

A normal jump creates an additional problem when used for a function call.

Suppose execution transfers to:

```text
function
```

After the function finishes, execution must resume at the correct point in the caller.

The system therefore needs to preserve a:

```text
return address
```

Conceptually:

```text
CALL target
↓
preserve return address
+
PC ← target
```

The return address identifies where execution should continue after the called function completes.

---

# Return Address

The return address is not generally the address of the last instruction executed before the call.

It represents the location at which execution must resume afterward.

Conceptually:

```text
caller
↓
CALL
↓
save resume location
↓
callee
...
↓
RET
↓
resume caller
```

How the return address is preserved depends on the architecture and execution environment.

It may be stored in a register on some architectures.

On the observed x86-64 machine, `CALL` and `RET` used the stack.

---

# RET and the Stack

Immediately before the observed `retq`, GDB reported:

```text
RSP = 0x7fffffffde18
RIP = 0x555555555140
```

Inspecting the value at the top of the stack produced:

```text
memory[RSP] = 0x555555555158
```

After one `retq` instruction:

```text
RSP = 0x7fffffffde20
RIP = 0x555555555158
```

The value previously found at:

```text
memory[RSP]
```

became the new instruction pointer.

Conceptually, the observed behavior was equivalent to:

```text
return_address ← memory[RSP]
RIP ← return_address
RSP ← RSP + 8
```

This provided direct evidence that the return address stored on the stack restored the caller's control flow.

---

# Stack Participation in Function Execution

The same experiment also exposed simple stack manipulation.

The function prologue contained:

```asm
push %rbp
mov %rsp,%rbp
```

`push %rbp` preserved the previous value of `RBP` on the stack and adjusted `RSP`.

The next instruction:

```asm
mov %rsp,%rbp
```

produced the observed transition:

```text
before:

RSP = 0x7fffffffde10
RBP = 0x7fffffffde20

after:

RSP = 0x7fffffffde10
RBP = 0x7fffffffde10
```

`RSP` remained unchanged during the `mov`.

`RBP` became equal to `RSP`.

This demonstrated a simple architectural state transformation without requiring knowledge of detailed calling conventions.

---

# Observing Operand Movement

The compiled addition function also contained:

```asm
mov %edi,-0x4(%rbp)
mov %esi,-0x8(%rbp)
```

With AT&T syntax:

```text
mov source, destination
```

These instructions therefore moved values:

```text
register
↓
memory
```

Later:

```asm
mov -0x4(%rbp),%edx
mov -0x8(%rbp),%eax
```

moved values in the opposite direction:

```text
memory
↓
register
```

This provided a concrete example of operand acquisition before arithmetic execution.

---

# Observing an Arithmetic State Transition

Immediately before:

```asm
add %edx,%eax
```

GDB showed:

```text
EAX = 7
EDX = 5
RIP = ...513d
```

After executing exactly that instruction:

```text
EAX = 12
EDX = 5
RIP = ...513f
```

The observed architectural transition was therefore:

```text
EAX: 7 → 12
EDX: unchanged
RIP: current instruction → next instruction
```

This provided direct evidence for the state-machine model.

```text
architectural state before
↓
ADD
↓
architectural state after
```

# Fetch, Decode and Execute

Only after deriving the required mechanisms can instruction execution be summarized using the familiar model:

```text
fetch
↓
decode
↓
execute
```

At a conceptual level:

```text
fetch
→ make instruction bytes available

decode
→ interpret those bytes according to the ISA

execute
→ perform the required state transformation
```

This abstraction is useful.

But it must not be mistaken for a universal literal description of how every modern processor internally schedules one instruction after another.

Real microarchitectures may overlap and reorganize internal work.

Those details belong primarily to later performance study.

---

# Fetch–Decode–Execute Is an Abstraction

The useful meaning of the model is:

```text
What instruction bytes are required?
↓
What do those bits mean?
↓
What state transformation must occur?
```

It should not imply:

```text
instruction 1:
fetch
decode
execute
complete

then instruction 2:
fetch
decode
execute
complete
```

as a universal physical rule.

The ISA constrains the observable result.

The microarchitecture determines how that result is internally realized.

---

# ISA vs Compiler vs Microarchitecture

Instruction execution requires keeping three different responsibilities separate.

The compiler translates higher-level source code into instructions belonging to a target ISA.

For example:

```c
if (a == 5)
```

may be translated by a compiler using:

```asm
cmp
jne
```

The compiler chooses that translation.

The ISA defines what instructions such as:

```text
CMP
JNE
MOV
ADD
RET
```

mean.

The microarchitecture determines how a particular processor internally implements those instructions.

Conceptually:

```text
source program
↓
compiler chooses instruction sequence
↓
ISA defines instruction meaning
↓
microarchitecture realizes execution
```

The ISA does not require a compiler to translate every source construct into one unique instruction sequence.

Different correct instruction sequences may implement the same source-level behavior.

---

# ISA Requirements

The ISA defines architectural semantics.

If an ISA defines an instruction conceptually as:

```text
ADD R2, R0, R1
```

then the required architectural result is:

```text
R2 ← R0 + R1
```

The implementation must honor that contract.

Similarly:

```text
LOAD R0, [A]
```

must produce the architecturally defined loaded value regardless of whether the data was found nearby or far down the memory hierarchy.

---

# Microarchitectural Freedom

The ISA does not necessarily dictate the exact internal hardware sequence used to produce an instruction's architectural result.

Two processors implementing the same ISA may therefore use different internal mechanisms.

Conceptually:

```text
ISA
→ defines required observable behavior

microarchitecture
→ chooses internal mechanisms
```

This distinction is essential.

Architectural state describes what software can rely upon.

Microarchitectural behavior describes how a particular processor implements that contract internally.

---

# Memory Hierarchy and Instruction Execution

Instruction Execution directly reconnects to Memory Hierarchy.

A load may require:

```text
address
↓
memory hierarchy
↓
required value
↓
register
```

Two executions of the same architectural `LOAD` may therefore have different costs.

The value loaded may be identical.

But one execution may find the value in a nearby cache while another may require data from a lower memory level.

Therefore:

```text
architectural result
→ unchanged

execution cost
→ potentially different
```

This is another example of the distinction between architectural correctness and microarchitectural cost.

# Manual State Tracing

A simplified conceptual machine was used to reason about execution.

For example:

```text
R0 = 5
R1 = 7
R2 = 0
PC = 100

100: ADD R2, R0, R1
104: CMP R2, 12
108: JNE 200
112: STORE [A], R2
116: JMP 204
200: STORE [B], R2
204: ...
```

The resulting transitions were traced individually.

After:

```text
ADD R2, R0, R1
```

the state contained:

```text
R2 = 12
PC = 104
```

After:

```text
CMP R2, 12
```

the relevant state became:

```text
ZF = 1
PC = 108
```

At:

```text
JNE 200
```

the jump was not taken because:

```text
ZF = 1
```

so:

```text
PC = 112
```

Then:

```text
STORE [A], R2
```

produced:

```text
memory[A] = 12
PC = 116
```

Finally:

```text
JMP 204
```

produced:

```text
PC = 204
```

Tracing instructions individually reinforces the central model:

> Each instruction produces its own architectural state transition.

# Core Mental Model

When reasoning about instruction execution, ask:

```text
Where does the current instruction begin?

What address does the Program Counter contain?

Have the instruction bytes become available?

How are those bits interpreted?

Which operation does the ISA define?

Which operands are required?

Where do those operands come from?

Are they registers, immediates or memory values?

Does execution require data movement?

Which architectural state changes?

Does the instruction update registers?

Does it update flags?

Does it update memory?

What becomes the next Program Counter?

Is control sequential or redirected?

Which behavior is required by the ISA?

Which choices belong to the compiler?

Which details belong to the microarchitecture?
```

The useful abstraction is:

```text
architectural state
↓
PC identifies instruction
↓
instruction bytes become available
↓
ISA gives those bytes meaning
↓
operands are identified
↓
operands become available
↓
required operation occurs
↓
architectural state changes
↓
next PC is determined
↓
next instruction
```

The processor continuously repeats this process from the architectural perspective.

The exact internal implementation may be significantly more complicated.

# Final Takeaway

A running program ultimately consists of encoded machine instructions.

The Program Counter identifies where execution should obtain the next instruction.

Those bytes must become available to the processor.

The ISA gives them meaning.

Decoding identifies the required operation and operands.

The operands may come from:

```text
registers
immediate values
memory
```

The required operation then transforms architectural state.

That transformation may affect:

```text
registers
flags
memory
Program Counter
```

Control-flow instructions make the role of the Program Counter especially visible.

Sequential execution selects the following instruction boundary.

A jump selects another address.

A conditional branch selects the next address based on architectural condition state.

A function call must preserve a return location.

A return restores execution from that location.

The familiar:

```text
fetch
↓
decode
↓
execute
```

model is therefore useful because it summarizes real conceptual requirements.

But it is an abstraction.

It does not require every processor to internally execute instructions through three isolated sequential hardware phases.

At the architectural level:

```text
instruction encoding
+
ISA
+
operands
+
current architectural state
↓
required state transformation
↓
next architectural state
```

At the implementation level:

```text
microarchitecture
→ determines how that result is physically realized
```

The essential model is:

> Instruction execution is the process by which the processor obtains an ISA-defined instruction, makes its required operands available, performs the required transformation, updates architectural state and determines which instruction should execute next.
