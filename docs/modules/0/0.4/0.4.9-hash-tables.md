# Systems Mastery 0.4.9 — Hash Tables

> Data structures optimize how information is organized. Hash tables optimize how information is found.

---

# Objective

Previous modules explored different ways of organizing information.

Arrays provide efficient access through position.

Linked structures provide flexible relationships.

Trees provide hierarchical organization.

Graphs provide arbitrary connections.

However, all of these structures share a common challenge:

> Finding a specific element requires some form of search.

For some problems, searching becomes the dominant cost.

This module asks a different engineering question:

> How can a system locate information without searching through the entire collection?

The purpose is not to memorize the implementation of hash tables.

The purpose is to understand why direct addressing is attractive but limited, why collisions are unavoidable, how hashing transforms lookup into a different problem, and how hash-based structures maintain correctness despite uncertainty.

---

# When Searching Stops Scaling

Many data structures rely on traversal to locate information.

A list requires scanning elements.

A tree requires following relationships.

A graph requires exploration.

For small datasets, this is acceptable.

For large systems, repeatedly asking:

> "Where is this element?"

can become the dominant operation.

The problem is not storing information.

The problem is locating it efficiently.

Hash tables exist to transform this question:

```text
Where is this element?

↓

Calculate where this element should be.
````

---

# Direct Addressing

The ideal solution is direct addressing.

The idea is simple:

```text
index = key
```

If the key is:

```text
42
```

the element is stored directly at:

```text
array[42]
```

Lookup becomes immediate.

No traversal.

No comparison.

No search.

The position is already known.

Direct addressing provides perfect lookup performance.

However, it requires the key space and memory space to be compatible.

---

# The Problem of Sparse Memory

Real systems rarely have dense keys.

Imagine storing:

```text
12
4,000,000
900,000,000
```

Using direct addressing requires an array large enough to contain:

```text
900,000,001 positions
```

even though only three elements exist.

Most allocated memory would remain unused.

The problem is not that direct addressing is incorrect.

The problem is that the key space can be much larger than the actual data.

A practical structure therefore needs to compress a large key space into a smaller memory space.

---

# Hash Functions

A hash function transforms a key into an array position.

Conceptually:

```text
key
 |
 v
hash function
 |
 v
bucket index
```

For example:

```text
index = key % capacity
```

With a capacity of `10`:

```text
12 → 2
42 → 2
57 → 7
```

The hash function allows a large set of possible keys to map into a smaller set of positions.

However, this creates a fundamental consequence.

Different keys can produce the same index.

---

# Collisions

A collision occurs when multiple keys map to the same bucket.

Example:

```text
12 → bucket 2
42 → bucket 2
```

Collisions are not implementation errors.

They are mathematically unavoidable whenever:

```text
possible keys > available positions
```

The purpose of a hash function is therefore not eliminating collisions.

Its purpose is distributing keys as evenly as possible.

A correct hash table must guarantee:

* no key is lost because of collisions;
* every stored key remains reachable;
* lookup can still identify the correct element.

---

# Collision Resolution

A hash table needs a strategy for storing multiple elements inside the same bucket.

Several approaches exist.

This module uses **separate chaining**.

---

# Separate Chaining

Each bucket stores a collection of entries instead of a single entry.

Conceptually:

```text
HashTable

bucket 0
    |
    ├── (12, value)
    └── (42, value)

bucket 1
    |
    └── (7, value)
```

The hash function performs the first step:

```text
key
 ↓
bucket
```

The bucket then performs a local search:

```text
bucket
 ↓
compare keys
 ↓
find matching entry
```

The hash table does not remove searching completely.

It reduces the search space.

Instead of searching the entire collection, it searches only the relevant bucket.

---

# The Cost of Poor Distribution

A hash table performs well when elements are distributed across buckets.

However, a bad distribution can collapse performance.

Worst case:

```text
all keys → same bucket
```

The structure becomes:

```text
bucket 0

├── key A
├── key B
├── key C
├── ...
```

Lookup becomes a linear scan.

The complexity degrades toward:

```text
O(n)
```

The hash table therefore depends on:

* good hash distribution;
* sufficient capacity;
* controlled load factor.

---

# Hash Table State

A hash table maintains information beyond the stored elements.

The structure must know:

* current capacity;
* number of stored entries;
* bucket distribution.

The number of stored elements is represented by:

```text
size
```

The structure maintains the invariant:

> size always equals the number of stored entries.

Updating an existing key does not increase size.

Adding a new key does.

---

# Lookup and Insertion

A hash table provides operations based on keys.

Insertion:

```text
put(key, value)
```

The algorithm:

* calculate the bucket;
* search the bucket for the key;
* update the value if the key exists;
* otherwise insert a new entry.

Lookup:

```text
get(key)
```

The algorithm:

* calculate the bucket;
* search only that bucket;
* return the associated value.

The hash function determines where to look.

The key comparison determines what was found.

---

# Load Factor

As more elements are inserted, buckets become increasingly populated.

The load factor measures this density:

```text
load factor = size / capacity
```

A low load factor:

```text
few elements
many buckets
```

means short bucket searches.

A high load factor:

```text
many elements
few buckets
```

means longer searches.

The load factor does not directly optimize the structure.

It indicates when the current capacity is no longer appropriate.

---

# Rehashing

When the load factor exceeds a threshold, the table increases its capacity.

However, resizing the array is not enough.

The position of an element depends on:

```text
index = hash(key) % capacity
```

Changing capacity changes the result.

Therefore, every element must be redistributed.

Rehashing performs:

* create a larger bucket array;
* recalculate the index of every entry;
* insert every entry into its new bucket.

The goal is not copying memory.

The goal is rebuilding the index.

---

# Hash Sets

A hash table stores:

```text
key → value
```

A set stores:

```text
element → existence
```

A set does not need an associated value.

It only needs to answer:

> Is this element present?

Because of this, a set can be implemented using a hash table:

```text
HashSet

    HashTable

        element → PRESENT
```

The stored value is only a placeholder.

The key itself represents membership.

---

# Composition Over Duplication

A hash set does not reimplement:

* hashing;
* buckets;
* collision handling;
* resizing;
* rehashing.

Instead:

```text
HashSet
    |
    v
HashTable
```

The set delegates storage and lookup to the hash table.

This follows a general engineering principle:

> Build new abstractions by composing existing components instead of duplicating their internal behavior.

The HashSet changes the meaning of the data, not the mechanism used to store it.

---

# Hash Tables in Real Systems

Hash-based structures appear throughout software engineering.

Examples:

* dictionaries and maps;
* caches;
* symbol tables in compilers;
* database indexes;
* memoization systems;
* visited-node tracking in graph algorithms.

Many systems repeatedly ask the same question:

> Has this thing already been seen?

Hash tables provide an efficient answer.

---

# Looking Beyond Hash Tables

Hash tables solve efficient lookup.

They do not solve every organization problem.

They do not naturally represent:

* ordered relationships;
* hierarchical structures;
* arbitrary networks;
* priority-based access.

Different problems require different structures.

The important engineering skill is recognizing the operation that needs optimization.

---

# Core Mental Model

When reasoning about hash tables, ask:

```text
What operation is becoming expensive?

Can the position of data be calculated?

Is the key space larger than available memory?

How are collisions handled?

What guarantees that no data is lost?

How dense is the table becoming?

When should the structure rebuild itself?

Is this really a map problem or a set problem?
```

The important concept is not the syntax of a hash table.

It is understanding that hashing replaces search with calculation, while additional mechanisms preserve correctness when that calculation is imperfect.
