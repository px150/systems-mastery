# Systems Mastery 0.4.10 — Heaps

> Some systems do not need to know where every element belongs. They only need to know what comes next.

---

# Objective

Previous modules explored structures optimized for different access patterns.

Arrays provide efficient access through position.

Linked structures provide flexible relationships.

Trees provide hierarchical organization.

Graphs provide arbitrary connections.

Hash tables provide efficient lookup through keys.

However, another class of problems asks a different question:

> Which element should be processed next?

A scheduler may need the highest-priority job.

A simulation may need the next event.

A routing algorithm may need the most promising candidate.

Keeping every element completely ordered can solve these problems, but often maintains more information than the system actually needs.

This module asks a different engineering question:

> How can a system efficiently maintain access to the highest-priority element without keeping the entire collection sorted?

The purpose is not to memorize heap operations.

The purpose is to understand partial ordering, the invariants that make priority-based access efficient, how array representation can encode tree structure implicitly, and why heaps provide an effective foundation for priority queues.

---

# Priority Without Full Ordering

Consider a collection of priorities:

```text
20
90
40
70
10
```

One solution is to keep them completely sorted:

```text
90
70
40
20
10
```

This makes the maximum immediately available.

However, every insertion may require finding the correct position and shifting existing elements.

The structure maintains information that a priority-oriented system may never use.

If the only important question is:

> What is the highest-priority element?

then knowing the exact relative order of every other element is unnecessary.

A heap solves this by maintaining only enough ordering to guarantee efficient access to the element that matters most.

---

# The Heap Property

A max-heap maintains a local invariant:

> Every parent is greater than or equal to its children.

For example:

```text
        90
       /  \
     70    80
    / \    / \
   20 50  60 40
```

The structure does not guarantee:

```text
70 > 60
50 > 40
```

or any other relationship between nodes that are not connected through a parent-child relationship.

It guarantees only:

```text
parent >= children
```

Because this invariant holds throughout the structure, the largest value must always be at the root.

This is the central idea of a heap:

> Global priority emerges from local ordering constraints.

---

# Complete Binary Trees

A binary heap is not an arbitrary binary tree.

It is a **complete binary tree**.

Every level is completely filled except possibly the last, and the last level is filled from left to right.

For example:

```text
        90
       /  \
     70    80
    / \    /
   20 50  60
```

is complete.

The complete-tree property keeps the structure compact and guarantees logarithmic height.

For `n` elements, the height grows as:

```text
O(log n)
```

This bounded height is what allows repair operations to remain efficient.

---

# Trees Without Tree Nodes

Although a heap is conceptually a tree, it does not require explicit tree nodes.

The complete-tree property allows the relationships to be calculated directly from array positions.

Consider:

```text
        90
       /  \
     70    80
    / \    / \
   20 50  60 40
```

The same structure can be stored as:

```text
[90, 70, 80, 20, 50, 60, 40]
```

For a node at index `i`:

```text
left child  = 2i + 1
right child = 2i + 2
parent      = (i - 1) // 2
```

No pointers are required.

No `TreeNode` objects are required.

The tree structure is implicit in the array layout.

This demonstrates an important systems principle:

> Logical structure does not require an identical physical representation.

---

# Inserting Into a Heap

A new value must first preserve the complete-tree property.

Because the heap is represented by an array, this means appending it to the end.

Consider:

```text
[60, 30, 50, 10, 20, 35]
```

Insert:

```text
40
```

The new element is appended:

```text
[60, 30, 50, 10, 20, 35, 40]
```

The complete-tree property remains valid.

However, the heap property may now be violated between the new node and its parent.

The structure must repair itself upward.

---

# Sift Up

Sift-up restores the heap property after insertion.

The algorithm repeatedly:

```text
compare node with parent

if node <= parent
    stop

otherwise
    swap node and parent
    continue from parent
```

Only the path from the inserted node toward the root can contain a violation.

The rest of the heap was already valid before insertion.

Because the height of the heap is:

```text
O(log n)
```

the maximum number of swaps is also:

```text
O(log n)
```

Therefore:

```text
insert → O(log n)
```

The important insight is that insertion does not rebuild or reorder the heap.

It repairs only the path that could have become invalid.

---

# Accessing the Maximum

The max-heap property guarantees that the maximum element is always at the root.

In the array representation, the root is:

```text
values[0]
```

Therefore:

```text
peek → O(1)
```

No traversal is required.

No search is required.

No comparison is required.

The structure continuously maintains the invariant that makes the answer immediately available.

---

# Extracting the Maximum

Removing the root creates two problems.

Consider:

```text
        90
       /  \
     70    80
    / \    / \
   20 50  60 40
```

Removing `90` directly would leave a hole at the root.

Instead, the last element is moved into the root position:

```text
        40
       /  \
     70    80
    / \    /
   20 50  60
```

This preserves the complete-tree property because the element removed from the physical structure came from the final array position.

However, the heap property is now violated.

The structure must repair itself downward.

---

# Sift Down

Sift-down restores the heap property after the root has been replaced.

At each step, the node is compared with its children.

For a max-heap, if a swap is necessary, the node must swap with the **larger child**.

Consider:

```text
        40
       /  \
     70    80
```

Swapping with `70` would produce:

```text
        70
       /  \
     40    80
```

which is still invalid.

Instead, the structure chooses `80`:

```text
        80
       /  \
     70    40
```

The heap property is now restored at that level.

The displaced value may still violate the property farther down, so sift-down continues along that branch.

The algorithm stops when:

```text
the node has no children
```

or:

```text
node >= largest child
```

Because only one path through the tree is followed:

```text
sift down → O(log n)
```

and therefore:

```text
extract max → O(log n)
```

---

# Two Heap Invariants

A binary heap depends on two distinct invariants.

The first is structural:

> The heap is a complete binary tree.

The second is ordering-based:

> Every parent satisfies the heap property relative to its children.

Insertion preserves the structural invariant by appending at the end, then restores ordering through sift-up.

Extraction preserves the structural invariant by removing the final element, then restores ordering through sift-down.

Understanding both invariants is essential.

The heap is not correct merely because the maximum happens to be at the root.

The entire structure must remain capable of supporting future operations efficiently.

---

# Building a Heap

A heap can be constructed by starting empty and inserting every value.

For `n` elements:

```text
n insertions
×
O(log n) per insertion
```

gives:

```text
O(n log n)
```

However, when all values already exist, a more efficient strategy is possible.

The array can be transformed directly into a heap.

This operation is called:

```text
heapify
```

---

# Bottom-Up Heapify

Consider:

```text
[12, 50, 3, 90, 40, 70, 20]
```

The corresponding tree is:

```text
        12
       /  \
     50    3
    / \   / \
   90 40 70 20
```

The leaves already satisfy the heap property because they have no children.

Only internal nodes can violate it.

The last internal node is located at:

```text
(n // 2) - 1
```

Heapify therefore processes internal nodes from the bottom upward:

```text
last internal node
        ↓
      ...
        ↓
       root
```

and performs sift-down from each one.

For the example:

```text
[12, 50, 3, 90, 40, 70, 20]

→ [12, 50, 70, 90, 40, 3, 20]

→ [12, 90, 70, 50, 40, 3, 20]

→ [90, 50, 70, 12, 40, 3, 20]
```

The final array satisfies the max-heap property.

---

# Why Heapify Is O(n)

At first glance, heapify appears to be:

```text
O(n log n)
```

because it performs many sift-down operations and a sift-down can cost O(log n).

However, this assumes every node can travel the full height of the heap.

That is not true.

Most nodes are near the bottom.

Approximately:

```text
1/2 of nodes can move 0 levels
1/4 of nodes can move at most 1 level
1/8 of nodes can move at most 2 levels
1/16 of nodes can move at most 3 levels
...
```

The number of nodes decreases as the possible cost increases.

The total work therefore behaves like:

```text
n/2 × 0
+
n/4 × 1
+
n/8 × 2
+
n/16 × 3
+ ...
```

This sum grows linearly with `n`.

Therefore:

```text
heapify → O(n)
```

This is an important complexity lesson:

> The worst-case cost of one operation cannot always be multiplied by the number of operations when different elements have different possible costs.

---

# Ownership of Initial Data

Building a heap from an existing array introduces an API design question.

If the heap directly stores the caller's list, heapify will reorder that list.

For example:

```text
caller values
     |
     v
heap values
```

Both names may refer to the same mutable object.

Heapifying through one reference therefore changes what the other reference observes.

A structure can avoid this by copying the input before heapifying it.

This establishes a clearer ownership boundary:

> Constructing an internal representation should not silently mutate caller-owned state unless the API explicitly promises that behavior.

This concern is not specific to heaps.

It appears whenever mutable data crosses abstraction boundaries.

---

# Priority Queues

A heap is a data structure.

A priority queue is an abstraction.

A priority queue answers questions such as:

```text
Which job should run next?
```

Its interface may expose operations such as:

```text
push(job, priority)
peek()
pop()
```

The caller does not need to know how priority is maintained internally.

A max-heap provides an efficient implementation because it maintains the highest priority at the root.

This distinction matters:

> Priority queue describes behavior. Heap describes one mechanism capable of providing that behavior.

---

# Priority and Payload

Real priority queues usually manage more than numbers.

Conceptually, an item contains:

```text
priority
+
payload
```

For example:

```text
90 → handle payment
50 → send email
20 → cleanup cache
```

The priority determines ordering.

The payload is the information the system actually wants to process.

These responsibilities should remain conceptually separate.

The system asks:

```text
Which priority comes next?
```

in order to determine:

```text
Which payload should be returned?
```

---

# Equal Priorities

Multiple items may have the same priority.

From the heap's perspective:

```text
50
50
```

are equivalent.

The heap property requires only:

```text
parent >= child
```

Equality therefore creates no violation.

However, a heap does not automatically guarantee insertion order between equal-priority elements.

If a system requires:

```text
same priority → FIFO order
```

then priority alone is insufficient.

An additional ordering rule must be introduced, such as an insertion sequence number.

This illustrates another systems principle:

> Stability is a separate guarantee and must be designed explicitly when the application requires it.

---

# Composing Structures

A priority queue does not necessarily need to store payloads directly inside the heap.

One possible design separates responsibilities:

```text
MaxHeap
    |
    └── priorities

Hash-based mapping
    |
    └── priority → jobs
```

The heap answers:

```text
What is the highest current priority?
```

The mapping answers:

```text
Which jobs belong to that priority?
```

This allows an integer heap to remain simple while another structure manages payloads.

However, composition introduces a new invariant:

> Every priority represented by the heap must correspond to valid jobs, and both structures must remain synchronized.

If a priority remains in the heap after its final job has been removed, the structures disagree about the state of the queue.

Correctness therefore depends not only on each component being correct individually, but also on the relationships between them.

---

# Multiple Indexes Over the Same Data

Real systems often need to answer different questions efficiently.

Consider a job system that needs:

```text
What job has the highest priority?
```

and:

```text
Where is job abc123?
```

A heap answers the first question efficiently.

It does not answer the second efficiently.

Searching for an arbitrary ID inside a heap may require:

```text
O(n)
```

A hash table can provide average:

```text
O(1)
```

lookup by ID.

A system may therefore maintain:

```text
MaxHeap
    → priority access

HashTable
    → ID access
```

These are different indexes over the same logical data.

The benefit is efficient access through multiple dimensions.

The costs are:

```text
additional memory
+
synchronization complexity
```

Every insertion, deletion, or modification must preserve consistency across all representations.

---

# Sorted Arrays vs Heaps

A sorted array can also provide immediate access to the maximum.

If the maximum is stored at the end:

```text
peek maximum    → O(1)
extract maximum → O(1)
```

However, maintaining the ordering during insertion requires:

```text
O(n)
```

because elements may need to be shifted.

An unsorted array makes the opposite trade-off:

```text
insert          → O(1)
find maximum    → O(n)
extract maximum → O(n)
```

A heap balances these operations:

```text
insert          → O(log n)
peek maximum    → O(1)
extract maximum → O(log n)
```

The heap does not outperform every alternative for every workload.

It provides a useful balance when insertion and priority-based extraction happen repeatedly.

---

# Workload Determines Structure

Suppose all elements are known in advance and the system will only extract them afterward.

A sorted array may be appropriate:

```text
sort once
then repeatedly remove from one end
```

But consider a dynamic workload:

```text
insert
extract
insert
insert
extract
insert
extract
...
```

Maintaining complete ordering repeatedly performs work the application does not require.

The heap instead maintains only the partial ordering necessary to identify the next element.

This leads to a broader engineering principle:

> Data structures should be selected according to the operations a workload performs most frequently, not according to which structure appears most generally powerful.

---

# Heaps in Real Systems

Priority-based structures appear throughout software systems.

Examples include:

* task schedulers;
* event simulation;
* shortest-path algorithms;
* graph search;
* network scheduling;
* resource allocation;
* job processing systems;
* timer and event queues.

These systems repeatedly ask some variation of:

> What should happen next?

The heap provides an efficient answer without requiring the entire collection to remain globally ordered.

---

# Looking Beyond Heaps

Heaps solve priority-based access.

They do not solve every lookup or ordering problem.

They do not naturally provide:

* efficient arbitrary-key lookup;
* complete sorted traversal;
* hierarchical ownership;
* arbitrary relationships;
* stable ordering between equal priorities.

A heap should therefore not be understood as a faster sorted array.

It provides different guarantees.

The important engineering skill is recognizing when the application needs:

```text
the best element
```

rather than:

```text
all elements in order
```

---

# Core Mental Model

When reasoning about heaps, ask:

```text
Do I need complete ordering or only the next element?

What invariant guarantees that the root is correct?

How is the complete-tree property preserved?

Which path can contain a violation after insertion?

Which path can contain a violation after extraction?

Why must sift-down choose the larger child?

Can the tree structure be represented implicitly?

Am I building incrementally or heapifying existing data?

Does the workload alternate between insertion and extraction?

Do I need another index for arbitrary lookup?

If multiple structures represent the same data, how is consistency preserved?
```

The important concept is not the syntax of sift-up or sift-down.

It is understanding that heaps deliberately maintain less ordering information than a sorted structure, allowing systems to efficiently answer a narrower but extremely common question:

> What should come next?
