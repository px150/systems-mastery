# Systems Mastery 0.4.11 — Searching

> Searching is the process of reducing a space of possible candidates until the target is found or no candidates remain.

---

# Objective

Previous modules explored structures optimized for different access patterns.

Arrays provide efficient access through position.

Linked structures provide flexible relationships.

Trees provide hierarchical organization.

Graphs provide arbitrary connections.

Hash tables provide efficient lookup through keys.

Heaps provide efficient access through priority.

However, many systems face a more general question:

> Where is the element I am looking for?

A collection may contain the target, but knowing that the data exists is not enough.

The system needs a strategy for locating it.

This module asks a different engineering question:

> How can a system efficiently reduce the set of possible locations until a target is found or proven absent?

The purpose is not to memorize search algorithms.

The purpose is to understand search as candidate elimination, how organization changes the information available to a search algorithm, why binary search depends on both ordering and representation, and when repeated searches justify maintaining additional searchable structure.

---

# Searching as Candidate Elimination

Consider an unordered collection:

```text
[42, 7, 91, 18, 63, 4, 55, 27]
```

Suppose the target is:

```text
55
```

Inspecting the first value tells us:

```text
42 != 55
```

This eliminates one candidate.

It tells us nothing about the remaining values.

The target could still be anywhere in:

```text
[7, 91, 18, 63, 4, 55, 27]
```

Searching can therefore be understood as maintaining a set of possible candidates and progressively eliminating them.

The central question becomes:

> How much of the remaining search space can each observation safely eliminate?

This perspective separates the fundamental problem from any particular algorithm.

---

# Linear Search

When the collection provides no useful ordering information, the safest strategy is to inspect elements sequentially.

Conceptually:

```text
compare current element with target

if equal
    return its position

otherwise
    continue
```

For example:

```text
[42, 7, 91, 18, 63, 4, 55, 27]
  ↑

42 != 55
```

then:

```text
[42, 7, 91, 18, 63, 4, 55, 27]
      ↑

7 != 55
```

and so on until the target is found.

The implementation is direct:

```python
def linear_search(values: list[int], target: int) -> int | None:
    for i in range(len(values)):
        if values[i] == target:
            return i

    return None
```

During iteration, the algorithm maintains an implicit invariant:

> Every position before the current position has already been inspected and does not contain the target.

If the target is never found, eventually every candidate has been eliminated.

The search space becomes empty and the function returns:

```text
None
```

A successful and an unsuccessful search therefore follow the same process.

The difference is simply whether a matching candidate is encountered before the search space is exhausted.

---

# Linear Search Complexity

If the target is the first element:

```text
1 comparison
```

Therefore:

```text
best case → O(1)
```

If the target is the final element, every element must be inspected:

```text
n comparisons
```

If the target does not exist, every element must also be inspected.

Therefore:

```text
worst case → O(n)
```

The important reason is not merely that linear search uses a loop.

It is that, in an unordered collection, an unsuccessful comparison usually eliminates only one candidate.

The algorithm has no information that would justify excluding anything else.

---

# Ordering Changes the Search Space

Now consider the same problem with ordered values:

```text
[4, 7, 18, 27, 42, 55, 63, 91]
```

Suppose the target is:

```text
55
```

If the algorithm compares the target with:

```text
27
```

it learns:

```text
55 > 27
```

Because the values are ordered, this comparison provides more information than it did in the unordered collection.

The algorithm now knows that:

```text
4
7
18
27
```

cannot contain the target.

Several candidates have been eliminated through one comparison.

Ordering therefore changes the search problem.

It allows the algorithm to reason not only about the inspected element, but also about elements that have not been inspected.

This leads to an important principle:

> Structure creates information that algorithms can use to avoid unnecessary work.

---

# Binary Search

If ordering allows one side of the search space to be eliminated, inspecting an element near the middle maximizes the amount of work that can potentially be avoided.

Binary search repeatedly applies this idea.

Given an active ordered range:

```text
[4, 7, 18, 27, 42, 55, 63, 91]
```

the algorithm examines the middle candidate.

Three outcomes are possible:

```text
target == middle
    → target found

target > middle
    → eliminate middle and everything to its left

target < middle
    → eliminate middle and everything to its right
```

The remaining search space is therefore approximately halved after every unsuccessful comparison.

Instead of:

```text
n
↓
n - 1
↓
n - 2
↓
...
```

the search behaves like:

```text
n
↓
n / 2
↓
n / 4
↓
n / 8
↓
...
↓
1
```

This repeated reduction is the source of binary search's efficiency.

---

# The Binary Search Invariant

Binary search can represent the active search space using two boundaries:

```text
low
high
```

The fundamental invariant is:

> If the target exists, it must be inside the interval `[low, high]`.

Initially:

```python
low = 0
high = len(sorted_values) - 1
```

so every element is a candidate.

The middle position is:

```python
mid = (low + high) // 2
```

If:

```python
sorted_values[mid] < target
```

then `mid` has already been disproven and every earlier element is also too small.

The new boundary must therefore be:

```python
low = mid + 1
```

Similarly, if:

```python
sorted_values[mid] > target
```

the new boundary becomes:

```python
high = mid - 1
```

Using:

```text
low = mid
```

or:

```text
high = mid
```

would incorrectly preserve a candidate that has already been disproven.

For sufficiently small intervals, it could also cause the same midpoint to be selected repeatedly.

The search would stop making progress.

This leads to another important invariant:

> Every unsuccessful iteration must make the active search space strictly smaller.

The search continues while:

```python
low <= high
```

When:

```text
low == high
```

one candidate still remains and must be inspected.

Only when:

```text
low > high
```

is the search space empty.

The complete implementation is:

```python
def binary_search(
    sorted_values: list[int],
    target: int,
) -> int | None:
    low = 0
    high = len(sorted_values) - 1

    while low <= high:
        mid = (low + high) // 2

        if sorted_values[mid] == target:
            return mid
        elif sorted_values[mid] < target:
            low = mid + 1
        else:
            high = mid - 1

    return None
```

The function assumes that the input is already ordered.

Sorting the input is not part of binary search.

---

# Binary Search Complexity

Binary search repeatedly halves the remaining candidate space.

For example:

```text
1024
↓
512
↓
256
↓
128
↓
64
↓
32
↓
16
↓
8
↓
4
↓
2
↓
1
```

Because:

```text
1024 = 2^10
```

only about ten reductions are required to reduce 1024 candidates to one.

For `n` elements:

```text
binary search → O(log n)
```

If the first midpoint already contains the target:

```text
best case → O(1)
```

The logarithmic behavior does not come from performing comparisons faster.

It comes from eliminating a large fraction of the remaining candidates after every comparison.

---

# Duplicate Values

Consider:

```text
[2, 5, 5, 5, 8]
```

with:

```text
target = 5
```

A basic binary search guarantees only that a matching position will be returned.

It does not guarantee which occurrence will be found.

A test such as:

```python
assert binary_search([2, 5, 5, 5, 8], 5) == 1
```

would therefore impose a stronger contract than the algorithm provides.

A test matching the actual contract can instead verify:

```python
values = [2, 5, 5, 5, 8]

index = binary_search(values, 5)

assert index is not None
assert values[index] == 5
```

If the required behavior were:

```text
return the first occurrence
```

then finding a match would not necessarily terminate the search.

The algorithm would need to continue searching toward the left.

This demonstrates an important testing principle:

> Tests should verify the guarantees of the abstraction rather than accidental details of one execution.

---

# Iterative vs Recursive Binary Search

Binary search can also be expressed recursively.

Conceptually:

```text
search(low, high)

target < middle
    → search(low, mid - 1)

target > middle
    → search(mid + 1, high)
```

The structural base case occurs when:

```text
low > high
```

because no candidates remain.

The recursive and iterative forms eliminate candidates in the same way.

Therefore both require:

```text
O(log n)
```

time.

However, their memory behavior differs.

The iterative version stores only a fixed amount of state:

```text
low
high
mid
```

Therefore:

```text
space → O(1)
```

The recursive version creates a stack frame for every recursive call.

Because recursion depth follows the repeated halving of the search space:

```text
space → O(log n)
```

The same algorithmic strategy can therefore have different auxiliary-space costs depending on how its state is represented.

---

# Representation Determines Search Cost

Binary search is often described simply as:

```text
O(log n)
```

However, this assumes that the middle element can be accessed efficiently.

Arrays provide random access.

For an array:

```text
values[i] → O(1)
```

so reaching each midpoint is inexpensive.

Now consider an ordered linked structure.

The ordering still allows the algorithm to determine which side could contain the target.

However, reaching the middle element requires traversal through preceding nodes.

Conceptually:

```text
head
 ↓
node
 ↓
node
 ↓
...
 ↓
middle
```

The algorithm can still reason about halves, but accessing the point at which each comparison must occur is no longer constant time.

This demonstrates an important systems principle:

> Algorithmic complexity depends on the cost of the operations provided by the underlying representation.

An algorithm cannot be evaluated independently from the structure on which it operates.

---

# Searching vs Indexing

Suppose an unordered collection must be searched once.

A linear scan costs:

```text
O(n)
```

Sorting the entire collection merely to enable one binary search may require more total work than simply performing the scan.

Now suppose the same collection must support millions of searches.

The trade-off changes.

Maintaining additional organization may become worthwhile because its cost is amortized across many future queries.

This is the transition from searching toward indexing.

Conceptually:

```text
without additional organization

query
  ↓
search original data
```

An index introduces another representation:

```text
query
  ↓
search index
  ↓
locate original data
```

The purpose of the additional structure is to make important access patterns cheaper.

However, the index introduces costs:

```text
additional memory
+
maintenance work
+
consistency requirements
```

Every modification to the underlying data may require corresponding changes to the index.

Searching and indexing therefore represent different trade-offs between immediate work and maintained organization.

---

# Exact Lookup vs Range Search

Different search patterns benefit from different representations.

Suppose a system stores millions of sessions and frequently asks:

```text
Find the session with ID X.
```

A hash table can organize the data as:

```text
session_id → session
```

and provide average:

```text
lookup → O(1)
```

Now suppose the system instead asks:

```text
Find every ID between A and B.
```

A hash table does not naturally preserve the ordering relationship required by the query.

An ordered representation can locate the beginning of the relevant range and then traverse the matching values.

Conceptually:

```text
locate beginning → O(log n)

visit results     → O(k)
```

where `k` is the number of matching values.

The total work becomes:

```text
O(log n + k)
```

Neither representation is universally superior.

Each is optimized for a different access pattern.

---

# Multiple Indexes Over the Same Data

Real systems often need to answer different kinds of queries efficiently.

Consider a user system that frequently needs:

```text
Find user with ID X.
```

and:

```text
Find users whose age is between 30 and 40.
```

One representation could provide:

```text
HashTable

user_id → user
```

for efficient exact lookup.

Another could maintain:

```text
ordered index by age
```

for efficient range queries.

These are different indexes over the same logical data.

The benefit is efficient access through multiple dimensions.

The costs are:

```text
additional memory
+
additional update work
+
synchronization complexity
```

Every insertion, deletion, or relevant modification must preserve consistency across all representations.

The same principle appeared previously when heaps and hash tables were combined to support different access patterns.

Searching makes the reason explicit:

> Data organization should reflect the questions the system needs to answer efficiently.

---

# Workload Determines Search Strategy

Consider two workloads over a large unordered collection.

The first performs only one search.

In that situation:

```text
linear search
```

may be appropriate because creating and maintaining additional organization would cost more than the single lookup justifies.

Now consider a system performing millions of exact lookups while records are continuously inserted and removed.

A hash-based representation may be more appropriate.

If the workload instead performs many range queries, ordered organization may provide more useful information.

The important question is therefore not:

> Which search algorithm is fastest?

It is:

> Which representation and search strategy best match the operations performed by the workload?

This is the same principle encountered throughout data structures.

Complexity becomes meaningful only when connected to the operations a real system performs.

# Searching in Real Systems

Search appears throughout software systems.

Examples include:

* database queries;
* configuration lookup;
* routing tables;
* symbol lookup;
* filesystem search;
* cache lookup;
* API filtering;
* log analysis;
* in-memory data processing.

These systems differ dramatically in scale and representation, but they repeatedly ask similar questions:

```text
What is the target?

What are the remaining candidates?

What information can eliminate candidates?

How expensive is access to each candidate?

How often will the search occur?

Would additional organization make repeated searches cheaper?

What does that organization cost to maintain?
```

Recognizing these questions is more important than recognizing a particular implementation of linear or binary search.

# Looking Beyond Searching

Linear search and binary search solve only part of the broader data-access problem.

Linear search works without additional organization but may inspect the entire collection.

Binary search exploits ordering but requires a representation capable of supporting its access pattern efficiently.

Hash tables provide efficient exact-key lookup but do not naturally support ordered range queries.

Indexes can accelerate important queries but consume memory and introduce maintenance requirements.

Searching should therefore not be understood as an isolated family of algorithms.

It sits at the intersection of:

```text
representation
+
available information
+
access pattern
+
workload
```

Future modules will explore how ordering itself can be created and maintained.

That raises the next engineering question:

> If ordering can make searching more powerful, what does it cost to create that ordering?

---

# Core Mental Model

When reasoning about searching, ask:

```text
What is the target?

What is the candidate space?

What does the organization of the data tell me?

How many candidates can each observation safely eliminate?

When is the search space empty?

Does the representation provide efficient access to the positions the algorithm needs?

Is this a one-time search or a repeated workload?

Would ordering or indexing justify its maintenance cost?

Does the workload need exact lookup, range lookup, or multiple access patterns?

If multiple indexes represent the same data, how is consistency preserved?
```

The important concept is not the syntax of linear search or binary search.

It is understanding that searching is a process of eliminating candidates using the information made available by the data's organization.

Linear search eliminates candidates individually.

Binary search uses ordering to eliminate approximately half of the remaining candidates at each step.

Indexes introduce additional organization so that important searches can avoid large parts of the original data entirely.

The central principle is:

> Search efficiency emerges from the relationship between information, representation and workload.
