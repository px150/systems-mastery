# Systems Mastery 0.4.12 — Sorting

> Sorting is the process of introducing order into data so that future operations can exploit that structure.

---

# Objective

The previous module explored searching as candidate elimination.

Unordered data provides little information about where a target may be located.

Ordered data changes the problem.

A comparison can eliminate entire regions of the search space, making strategies such as binary search possible.

However, that organization is not free.

Before a system can exploit ordering, the order must first be created or maintained.

This module asks the next engineering question:

> What does it cost to create order, and when is that cost worth paying?

The purpose is not to memorize sorting algorithms.

The purpose is to understand sorting as a transformation of representation, how different strategies maintain different invariants, why input structure affects algorithmic behavior, how time and memory trade against each other, and when sorting should be replaced by continuously maintained organization.

---

# Sorting as Creating Structure

Consider an unordered collection:

```text
[7, 3, 9, 2, 5, 8, 1, 4]
```

The values exist, but their positions provide little useful information.

For example, knowing that:

```text
7 > 5
```

does not tell us where `5` might appear elsewhere in the collection.

After sorting:

```text
[1, 2, 3, 4, 5, 7, 8, 9]
```

position begins to carry information.

Values before a position are smaller.

Values after it are larger.

This organization can support operations such as:

```text
binary search
range queries
ordered traversal
deduplication
merging
reporting
```

Sorting therefore performs work now so that later operations can exploit additional structure.

This leads to an important principle:

> Sorting is useful when the value of the resulting organization justifies the cost of creating it.

---

# Sorting Through Invariants

A sorting algorithm transforms an unordered collection into an ordered one.

During that transformation, however, the entire collection is usually not ordered yet.

The algorithm therefore needs a property that remains true while progress is made.

That property is an invariant.

Different sorting algorithms can solve the same final problem while maintaining fundamentally different invariants.

Understanding those invariants is more useful than memorizing their implementations.

---

# Selection Sort

One possible strategy is to determine the final contents of the collection one position at a time.

Suppose the collection is:

```text
[7, 3, 9, 2, 5]
```

At position `0`, the algorithm searches the entire remaining collection for the smallest value:

```text
2
```

and moves it into position:

```text
[2 | 3, 9, 7, 5]
```

The first position is now final.

The algorithm repeats the process over the remaining suffix.

Find the smallest remaining value:

```text
3
```

giving:

```text
[2, 3 | 9, 7, 5]
```

Then:

```text
[2, 3, 5 | 7, 9]
```

and eventually:

```text
[2, 3, 5, 7, 9]
```

The fundamental invariant is:

> Before iteration `i`, every position before `i` contains its final globally correct value.

The prefix is not merely sorted internally.

Its elements will never need to move again.

---

# Selection Sort Implementation

The algorithm can represent the beginning of the unsorted region using `i`.

Within that region, it searches for the minimum value:

```python
def selection_sort(values: list[int]) -> None:
    for i in range(len(values) - 1):
        min_index = i

        for j in range(i + 1, len(values)):
            if values[j] < values[min_index]:
                min_index = j

        values[i], values[min_index] = values[min_index], values[i]
```

The outer loop determines which position is being finalized.

The inner loop discovers which remaining value belongs there.

After the swap:

```text
values[:i + 1]
```

contains globally finalized values.

---

# Selection Sort Complexity

The first iteration examines approximately:

```text
n
```

elements.

The next examines:

```text
n - 1
```

then:

```text
n - 2
```

and so on.

The total work resembles:

```text
n + (n - 1) + (n - 2) + ... + 1
```

which grows quadratically.

Therefore:

```text
selection sort → O(n²)
```

This remains true even if the input is already sorted.

For example:

```text
[1, 2, 3, 4, 5]
```

The algorithm still has to inspect the remaining suffix before it can prove that each current value is the minimum.

Selection sort therefore does not substantially benefit from existing order.

Its auxiliary memory requirement, however, is constant:

```text
space → O(1)
```

because the collection is rearranged in place and only a small amount of additional state is maintained.

---

# Insertion Sort

A different strategy is to maintain an already sorted region and insert each new value into the correct position within it.

Consider:

```text
[7, 3, 9, 2, 5]
```

A single element is trivially sorted:

```text
[7]
```

Now consider `3`.

It belongs before `7`:

```text
[3, 7]
```

Next comes `9`:

```text
[3, 7, 9]
```

Then `2`:

```text
[2, 3, 7, 9]
```

and finally `5`:

```text
[2, 3, 5, 7, 9]
```

The invariant differs from selection sort:

> Before iteration `i`, the prefix `values[:i]` is sorted relative to the elements processed so far.

The values in that prefix are not necessarily in their final global positions.

For example:

```text
[2, 4, 7 | 9, 5, 8, 6]
```

is a valid insertion-sort state.

The prefix:

```text
[2, 4, 7]
```

is sorted.

However, when `5` is eventually processed, it will be inserted before `7`.

This would not be a valid finalized prefix for selection sort.

---

# Insertion Through Shifting

Suppose the sorted prefix is:

```text
[2, 4, 7, 9]
```

and the next value is:

```text
5
```

The algorithm temporarily stores `5`.

Values larger than it are shifted right:

```text
[2, 4, 7, 9, 9]
[2, 4, 7, 7, 9]
```

The resulting gap is then filled:

```text
[2, 4, 5, 7, 9]
```

The implementation is:

```python
def insertion_sort(values: list[int]) -> None:
    for i in range(1, len(values)):
        current = values[i]
        j = i - 1

        while j >= 0 and values[j] > current:
            values[j + 1] = values[j]
            j -= 1

        values[j + 1] = current
```

The algorithm maintains the sorted-prefix invariant after every insertion.

---

# Insertion Sort Complexity

If the collection is already sorted:

```text
[1, 2, 3, 4, 5]
```

each new value is already correctly positioned relative to the prefix.

The inner loop performs no shifts.

Therefore:

```text
best case → O(n)
```

Now consider reverse order:

```text
[5, 4, 3, 2, 1]
```

Each new value must move through the entire sorted prefix.

The number of shifts resembles:

```text
1 + 2 + 3 + ... + (n - 1)
```

Therefore:

```text
worst case → O(n²)
```

Insertion sort and selection sort therefore share the same quadratic worst-case complexity.

Their behavior is nevertheless different.

Insertion sort can exploit existing order.

Selection sort continues searching the remaining suffix regardless of how ordered the input already is.

This demonstrates an important principle:

> The same asymptotic worst-case complexity does not imply the same behavior on real workloads.

Insertion sort also rearranges the collection in place:

```text
space → O(1)
```

---

# Divide and Conquer

Selection sort and insertion sort build order incrementally.

Another strategy is to transform one large sorting problem into several smaller sorting problems.

Consider:

```text
[7, 3, 9, 2, 5, 8, 1, 4]
```

Split it:

```text
[7, 3, 9, 2]    [5, 8, 1, 4]
```

Split again:

```text
[7, 3] [9, 2]    [5, 8] [1, 4]
```

and again:

```text
[7] [3] [9] [2] [5] [8] [1] [4]
```

A collection containing zero or one element is already sorted.

This provides the recursive base case.

The remaining problem is:

> How can two already sorted collections be combined into one sorted collection?

---

# Merging Sorted Collections

Suppose:

```text
left  = [2, 5, 8]
right = [1, 4, 9]
```

Because both collections are already sorted, the globally smallest remaining value must be at the front of one of them.

Compare:

```text
2
1
```

Choose `1`.

Then compare:

```text
2
4
```

Choose `2`.

Then:

```text
5
4
```

Choose `4`.

The process continues until one side is exhausted.

Any remaining elements on the other side can then be appended directly because that side is already sorted.

Conceptually:

```text
compare fronts
    ↓
take smaller
    ↓
advance only that side
    ↓
repeat
```

Each element is transferred once.

Therefore merging `n` total elements requires:

```text
O(n)
```

time.

---

# Merge Implementation

A linear merge can be implemented using independent positions for the two input collections:

```python
def merge(left: list[int], right: list[int]) -> list[int]:
    result = []

    left_i = 0
    right_i = 0

    while left_i < len(left) and right_i < len(right):
        if left[left_i] <= right[right_i]:
            result.append(left[left_i])
            left_i += 1
        else:
            result.append(right[right_i])
            right_i += 1

    while left_i < len(left):
        result.append(left[left_i])
        left_i += 1

    while right_i < len(right):
        result.append(right[right_i])
        right_i += 1

    return result
```

The function assumes that:

```text
left is sorted
right is sorted
```

This is a precondition of the merge operation.

Merge sort will recursively establish that precondition.

---

# Representation Can Change Algorithmic Cost

A superficially simpler implementation could repeatedly remove the first element:

```python
left.pop(0)
```

or:

```python
right.pop(0)
```

The algorithmic idea appears unchanged.

However, Python lists are array-backed structures.

Removing the first element requires later elements to be shifted.

Therefore:

```text
pop(0) → O(n)
```

Repeated inside the merge loop, this can destroy the intended linear behavior of the merge.

Using indexes instead:

```text
left_i
right_i
```

avoids those shifts.

This demonstrates a principle encountered throughout Systems Mastery:

> Algorithmic complexity depends on the operations provided by the underlying representation.

An abstract algorithm cannot be evaluated independently from its concrete data structure.

---

# Merge Sort

Merge sort combines recursive decomposition with linear merging.

The implementation follows three stages:

```text
divide
solve
combine
```

In code:

```python
def merge_sort(values: list[int]) -> list[int]:
    if len(values) <= 1:
        return values

    mid = len(values) // 2

    left = merge_sort(values[:mid])
    right = merge_sort(values[mid:])

    return merge(left, right)
```

The base case is:

```text
zero or one element
```

because such a collection is already sorted.

The recursive calls establish:

```text
left is sorted
right is sorted
```

which satisfies the precondition required by `merge`.

---

# Merge Sort Complexity

Consider eight elements.

The collection can be halved:

```text
8
↓
4
↓
2
↓
1
```

The number of division levels is:

```text
log₂(8) = 3
```

More generally:

```text
number of levels → O(log n)
```

At each merge level, every element participates in the merging work.

Across one complete level:

```text
work → O(n)
```

Therefore:

```text
O(n) work per level
×
O(log n) levels
```

gives:

```text
merge sort → O(n log n)
```

Unlike insertion sort, merge sort does not depend on the input being nearly sorted to obtain this asymptotic behavior.

For large randomly ordered collections, this difference becomes significant compared with quadratic sorting strategies.

---

# Time vs Space

Time complexity is not the only resource an algorithm consumes.

Selection sort and insertion sort rearrange the original collection directly.

Their auxiliary space is:

```text
O(1)
```

The merge sort implementation above creates:

```text
left slices
right slices
merge results
```

and therefore requires additional memory proportional to the input.

Conceptually:

```text
auxiliary space → O(n)
```

This creates a trade-off.

A system with a large collection and sufficient memory may prefer the improved time complexity of merge sort.

A memory-constrained system may care more strongly about avoiding additional proportional storage.

This demonstrates:

> An algorithm cannot be selected from time complexity alone.

The relevant resources include both execution work and memory consumption.

---

# Stability

Sorting records introduces another question.

Consider data that is already ordered by name:

```text
(Alice, 30)
(Bob,   25)
(Carol, 30)
(Dave,  25)
```

Now sort only by age.

A stable result is:

```text
(Bob,   25)
(Dave,  25)
(Alice, 30)
(Carol, 30)
```

Among records with equal age:

```text
Bob remains before Dave
Alice remains before Carol
```

A stable sorting algorithm guarantees:

> Elements with equal sorting keys preserve their original relative order.

This matters because equal keys may still carry meaningful ordering from a previous operation.

Stability therefore preserves information that is not represented by the current sorting key.

---

# Stability in Merge Sort

During merge sort, elements in the left half originally preceded elements in the right half.

Suppose two records have equal keys:

```text
left[left_i]  = (Alice, 30)
right[right_i] = (Carol, 30)
```

Using:

```python
if left[left_i] <= right[right_i]:
```

selects the left element first when the keys are equal.

The original relative order is preserved.

Using:

```python
if left[left_i] < right[right_i]:
```

would instead enter the `else` branch when the keys are equal.

The right element would be selected first.

The resulting collection could still be correctly ordered by the sorting key while no longer being stable.

This demonstrates:

> Correct ordering and stable ordering are different guarantees.

Tests must therefore verify stability explicitly when stability is part of the required contract.

---

# Sorting and Searching

The previous module showed that ordered data enables binary search.

However, sorting merely to perform one search may be wasteful.

Suppose an unordered collection contains `n` elements.

One linear search costs:

```text
O(n)
```

Sorting first using merge sort and then performing binary search costs approximately:

```text
sorting       → O(n log n)
binary search → O(log n)
```

For a single query, the initial sorting cost dominates.

Now suppose the same collection must support thousands or millions of searches.

The sorting cost can be paid once:

```text
sort → O(n log n)
```

and reused by later searches:

```text
search → O(log n)
search → O(log n)
search → O(log n)
...
```

The initial organization can therefore be amortized across future operations.

This connects sorting directly to the previous module:

> The value of ordering depends on how often future operations can exploit it.

---

# Sorting vs Maintaining Order

Sorting is not the only way to obtain ordered data.

A system may choose between:

```text
store cheaply
↓
sort when needed
```

and:

```text
maintain useful organization
during every update
```

Neither strategy is universally superior.

Consider:

```text
1,000,000 writes
1 ordered read
```

Maintaining expensive ordering during every write may perform unnecessary work.

Sorting when the result is actually required may be more appropriate.

Now consider:

```text
100 writes
10,000 ordered reads
```

Paying additional cost during the relatively rare updates may make the much more frequent reads cheaper.

The relevant question is therefore:

> When should the system pay the cost of organization?

The answer depends on the workload.

---

# Different Structures Preserve Different Information

Sorting is only one form of organization.

Suppose a job queue needs only:

```text
the highest-priority job
```

Maintaining a complete global ordering may preserve more information than the system needs.

A heap provides the required priority access without fully sorting every element.

Suppose instead the system needs:

```text
find user with ID X
```

A hash table may provide a better representation because the access pattern is exact-key lookup.

Now consider:

```text
find every product with price between 50 and 100
```

An ordered index preserves the relationship required for efficient range queries.

The correct representation depends on the information the workload needs.

This leads to a broader principle:

> Do not maintain more order than the operations of the system can justify.

---

# Multiple Representations of the Same Data

A system may need several access patterns simultaneously.

Consider users represented as:

```text
(id, name, age)
```

The system may frequently need:

```text
find user with ID X
```

and:

```text
find users whose age is between 30 and 40
```

One representation could maintain:

```text
HashTable

user_id → user
```

for efficient exact lookup.

Another could maintain:

```text
ordered index by age
```

for efficient range queries.

These structures represent different organizations over the same logical records.

The benefit is that each important access pattern receives an appropriate representation.

The costs include:

```text
additional memory
+
additional update work
+
consistency requirements
```

Every relevant modification must preserve all representations.

Sorting therefore connects naturally to indexing and system design.

---

# Workload Determines Sorting Strategy

There is no universally best sorting algorithm or organization strategy.

Consider a small collection that is already almost ordered.

Insertion sort may be appropriate because it can exploit the existing structure and requires only constant auxiliary space.

Consider a large randomly ordered collection with sufficient available memory.

Merge sort may be more appropriate because its:

```text
O(n log n)
```

time complexity scales better than quadratic alternatives.

Consider a system that only needs repeated access to the highest-priority item.

A heap may remove the need for complete sorting entirely.

Consider a system dominated by exact-key lookup.

A hash table may preserve more useful information than ordering.

The important question is therefore not:

> Which sorting algorithm is fastest?

It is:

> What organization does this workload need, and when should the system pay the cost of creating or maintaining it?

# Looking Beyond Sorting

Selection sort demonstrates how final positions can be established incrementally.

Insertion sort demonstrates how an ordered region can be maintained as new values are incorporated.

Merge sort demonstrates how divide-and-conquer can transform a quadratic problem into one requiring:

```text
O(n log n)
```

time.

But sorting is not an isolated operation.

It interacts with:

```text
representation
+
searching
+
indexing
+
memory
+
update frequency
+
access patterns
```

A system may sort once and reuse the result.

It may repeatedly sort changing data.

It may maintain ordered indexes continuously.

Or it may avoid complete ordering because a hash table, heap, or another specialized structure better matches the workload.

Sorting therefore represents a broader engineering decision:

> How much organization should the system maintain, and when is that organization worth its cost?

# Core Mental Model

When reasoning about sorting, ask:

```text
What ordering does the system actually need?

What invariant does the algorithm maintain while creating that order?

Which parts of the collection are already guaranteed to be correct?

How much work does each iteration or recursion level perform?

Does the algorithm exploit existing order?

What is the worst-case behavior?

What is the best-case behavior?

How much auxiliary memory does the implementation require?

Does the underlying representation make the assumed operations cheap?

Does stability matter?

Will the resulting order be reused?

How frequently does the data change?

Would maintaining order continuously be cheaper than repeatedly sorting?

Would a heap, hash table, or ordered index better match the required access pattern?
```

The important concept is not the syntax of selection sort, insertion sort, or merge sort.

It is understanding sorting as the deliberate creation of information through order.

Selection sort finalizes global positions one at a time.

Insertion sort maintains an ordered prefix and exploits existing order.

Merge sort recursively creates sorted regions and combines them efficiently.

The central principle is:

> The value of sorting emerges from the relationship between ordering cost, representation, workload, and the operations that can exploit the resulting structure.
