# Systems Mastery 0.4.7 — Graphs

> Trees organize hierarchy. Graphs organize relationships without imposing hierarchy.

---

# Objective

The previous modules introduced arrays, linked structures and trees.

Each structure progressively relaxed previous assumptions while introducing new ways of representing relationships.

Arrays organize contiguous memory.

Linked structures organize sequential relationships.

Trees organize hierarchical ownership.

Many real systems, however, cannot be described by hierarchy alone:

* Road networks connect cities.
* Social networks connect people.
* Computer networks connect machines.
* Package managers connect software dependencies.
* State machines connect possible transitions.

None of these systems naturally possesses a single root or a unique parent for every element.

This module asks a different engineering question:

> How can arbitrary relationships be represented without imposing hierarchy?

The purpose is not to memorize graph terminology.

The purpose is to understand why graphs exist, why trees are only one specialization of graphs, and how removing hierarchical constraints fundamentally changes the kinds of systems that can be modeled.

---

# From Hierarchy to Relationships

Trees successfully represent ownership.

Every node belongs to exactly one parent.

The structure itself defines a hierarchy.

Graphs deliberately remove this restriction.

Nodes may be connected for any reason.

Relationships no longer imply ownership.

They simply express that two entities are related.

The meaning of a relationship depends entirely on the problem being modeled.

The graph itself remains neutral.

---

# Graphs as a Generalization

A tree is not an alternative to a graph.

A tree is a graph that satisfies additional structural constraints.

Those constraints include:

* hierarchical relationships;
* exactly one parent for every non-root node;
* absence of cycles.

Removing these restrictions immediately produces the more general graph model.

Graphs therefore represent the broader abstraction.

Trees specialize it.

---

# Nodes and Edges

A graph consists of two fundamental concepts.

Nodes represent entities.

Edges represent relationships between entities.

Neither concept implies hierarchy.

Edges simply express connectivity.

The interpretation of that connectivity belongs entirely to the application domain.

A road.

A friendship.

A dependency.

A communication channel.

All may be represented by the same underlying abstraction.

---

# Directed Relationships

Relationships are not always symmetric.

If one package depends upon another, the opposite is not automatically true.

If one web page links to another, the destination does not necessarily link back.

For this reason, our implementation models a directed graph.

Each edge possesses a direction.

```text
A → B
```

does not imply

```text
B → A
```

These are two independent relationships.

---

# Graph Structure

Unlike trees, graphs do not distinguish parent and child nodes.

Every node simply maintains the set of neighboring nodes that are directly reachable through outgoing edges.

The graph itself owns the collection of nodes.

Individual nodes own only their outgoing relationships.

Hierarchy disappears.

Connectivity remains.

---

# Graph Invariants

Our graph implementation intentionally enforces several invariants:

* Each node may belong to the graph only once.
* Edges may only connect nodes already belonging to the graph.
* Duplicate directed edges are rejected.
* Self-loops are rejected.

These constraints are implementation decisions rather than universal graph properties.

They simplify the model while preserving the essential concepts introduced by this module.

---

# Identity Rather Than Value

Graph nodes represent entities rather than values.

Two different nodes may legitimately contain identical values.

They nevertheless remain distinct entities.

For this reason, graph membership is determined by object identity rather than structural equality.

The implementation therefore compares nodes using identity instead of value equality.

The graph distinguishes objects.

Not merely the data they contain.

---

# Graph Connectivity

A graph does not need to form a single connected structure.

Multiple disconnected components may coexist inside the same graph.

Some nodes may even possess no relationships at all.

Such isolated nodes still belong to the graph.

Connectivity therefore becomes a property of the relationships rather than a property of the graph itself.

---

# Representation Choices

Graphs admit many valid internal representations.

This module adopts a deliberately simple model.

The graph stores its nodes.

Each node stores its outgoing neighbors.

More sophisticated representations—such as adjacency matrices or centralized adjacency lists—will become relevant when algorithmic efficiency becomes the primary concern.

At this stage, conceptual clarity is more important than optimization.

---

# Graphs in Real Systems

Graphs naturally appear throughout software engineering.

* Social networks connect users.
* Road systems connect locations.
* Hyperlinks connect documents.
* Build systems connect software dependencies.
* Distributed systems connect services.
* Artificial intelligence models connect computational operations.

Although these systems solve completely different problems, they all rely upon the same fundamental abstraction.

Entities connected by arbitrary relationships.

---

# Looking Beyond Representation

Representing relationships is only the first step.

Once arbitrary connectivity exists, software must explore it.

Unlike trees, graphs may contain cycles.

Nodes may be reachable through multiple paths.

Traversal therefore becomes significantly more complex.

The following module introduces systematic graph exploration and the algorithms required to visit connected nodes safely and efficiently.

---

# Core Mental Model

When reasoning about graphs, ask:

```text
Are these relationships hierarchical or arbitrary?
Does direction matter?
What does an edge represent in this domain?
Can two nodes contain the same value?
Should identity or equality define graph membership?
Which structural constraints belong to the graph itself?
Which constraints belong only to this implementation?
```

These questions matter more than memorizing graph terminology.

They transform graphs from another data structure into a general model for representing arbitrary relationships.
